## State transitions and asynchronous rules

An eligible owner begins with a capability/profile refresh, then an authoritative saved address and an independent draft. Missing, pending, and approved addresses all permit editing once capability and profile loading finish. A normalized draft equal to the saved address is clean and cannot trigger storage. A different valid draft enables Save. Invalid draft input remains editable with explicit validation feedback and no request.

A save captures the normalized email, initiating caller, bound target, owner generation, and existing mutation token before scheduling. Admission immediately sets busy, clears prior operation results, and excludes a duplicate click. The operation checks cancellation and current owner/target before PUT, after PUT, before and after any verification POST, before and after private reconciliation, and before publishing a result. Keep all checks/publications on the same UI dispatcher as invalidation. The existing active-token comparison prevents an obsolete `finally` from clearing a newer operation's busy state.

The enabled path continues to use a confirmed PUT, the exact-address verification POST, and a private GET. The disabled path uses PUT and private GET with no POST. Keep a verification outcome local until reconciliation completes, so a `Sent` response cannot briefly appear as success for a different or unconfirmed current address. A matched final private profile publishes its true approval flag and any appropriate delivery result. Normally the replacement is pending because the repository reset approval; if the new address was independently verified before the GET, the authoritative approved flag wins. Do not synthesize a persistent false approval value in the client.

A false PUT or ordinary transport exception produces `SaveFailed`, performs only a still-current private reconciliation, and never requests verification. Cancellation propagates. A failed secondary GET keeps the primary failure, sets the separate load-failure indicator, and blocks further mutation until Refresh confirms a usable profile; do not allow a stale cached profile to keep Save enabled after reconciliation failure. A successful PUT followed by failed or mismatched reconciliation cannot display completed storage or delivery success. Show the load/changed-address message and preserve the draft for correction or retry. No automatic retry of the PUT is added because an uncertain response may follow a committed write.

Resend captures the saved pending address from the private record, never the draft, and performs no PUT. It retains the current server outcomes `Sent`, `AlreadyApproved`, `Unavailable`, `NoEmail`, `EmailChanged`, and `DeliveryFailed`, followed by private reconciliation. A concurrent changed/cleared record suppresses a stale success and presents explicit changed/missing feedback. An unsaved replacement draft survives the resend and subsequent GET. Manual refresh or node resume while busy is coalesced through `pendingEmailRefresh` and runs only after the matching active mutation finishes; it cannot transfer that mutation to a newer owner or target.

Owner loss, logout, selected-user change, and node destruction cancel obsolete work. Owner/target changes also increment the existing generation and clear private state before allowing a new owner's state to load. An old operation must not post, refresh, publish approval/success, navigate, clear newer errors, or release a newer busy state after invalidation. Retargeted live nodes use the same checks as changed callers. Node destruction follows the existing lifecycle cancellation rather than creating an application-wide job. No request is retargeted by changing a captured user ID.

## Known limits and handoff

HTTP cancellation cannot undo a PUT already accepted by the server, and a lost response cannot establish whether storage committed. Explicit uncertainty plus a private refresh is the intended recovery. The existing PUT has no compare-and-set old-email argument, so concurrent clients remain server-serialized last-writer behavior; the client can reject an observed mismatched final value and suppress false success but cannot add cross-client transaction guarantees without changing the endpoint. The existing expected-email verification request and conditional approval already prevent an old link from approving a replacement.

The current model observes session changes through caller identity and the authorized Boolean, not a credential epoch. Token refresh while the same owner remains authorized is not a new owner generation. The planned guarantees cover observed logout/identity/selection changes and canceled lifecycle work; they do not claim atomicity between shared HTTP bearer-token loading and a separate session switch. A project-wide credential generation or pinned-session transport would be a separate, evidence-driven auth task. Do not hide this limitation behind stronger prose or add such infrastructure to issue #79 without Architecture identifying a direct unmet acceptance condition.
