## Mutation sequence, serialization, and errors

`beginEmailMutation` admits both confirmed capability values, checks the raw owner/target and load-failure flag, and synchronously reserves the active token and busy state before launching. Save/resend enforce their distinct validation and verification prerequisites before admission. Retain lazy job registration in `launchEmailMutation`, one active mutation, owner generation, refresh version, and identity-based active-token comparison. Double clicks, Save plus Resend, and stale enabled buttons cannot queue a second mutation.

For enabled SMTP, the sequence is PUT B, private GET confirming owner/B, POST with the confirmed record's exact B when pending, and a final private GET before publishing completed storage/delivery feedback. This intentionally tightens Planning's PUT/POST/GET order. The first private read is a prerequisite for sending; the second prevents a late successful POST from producing feedback for a superseded address. If the first matching record is already approved because another verification completed, skip POST and expose its authoritative approved state. A normally replaced approved A must appear as B with `emailApproved=false`; do not synthesize approval in the client.

For disabled SMTP, the sequence is PUT B and private GET confirming owner/B, with zero verification calls. Publish address-bound saved feedback and display the existing delivery-unavailable copy from the confirmed capability. Do not fabricate a server verification result when no POST occurred. The enabled label remains “Save and send verification”; the disabled label is “Save email”.

A false PUT or ordinary transport exception records `SaveFailed`, reconciles only while the initiating mutation remains current, preserves the replacement draft, and never POSTs. Cancellation propagates. A true PUT with a failed/null/wrong-owner first GET has no completed success and no POST. A true PUT with a same-owner different or cleared address records `EmailChanged`, retains B, and makes no POST. A final GET mismatch similarly suppresses saved, `Sent`, and `AlreadyApproved` success. Keep the actual refreshed address/approval visible for the still-current owner when available. Ordinary failed reads keep explicit load feedback and require Refresh before another mutation.

Keep POST outcomes local until final reconciliation. `DeliveryFailed`, `Unavailable`, `NoEmail`, and `EmailChanged` remain explicit delivery/account outcomes; a POST exception maps to the existing `DeliveryFailed`. When final GET still confirms B after acknowledged PUT, storage confirmation can coexist with failed delivery. When final GET fails, retain the primary negative outcome and show the load error, but publish no success. `AlreadyApproved` may be displayed as successful only when the final B record is approved. `Sent` must not survive a final different or missing address. If a server outcome and the final record contradict each other, the authoritative profile controls status and the local changed-address error replaces contradictory success.

`onResendEmailVerification` reads the saved pending email from the latest matching private profile, never from the draft. It requires enabled SMTP and issues POST followed by a checked private GET, without PUT. With saved A and dirty draft B, its recipient remains A and B survives every outcome. Before the call, verify the captured profile still belongs to the current owner/target; the server's `expectedEmail` comparison handles remote changes after the last refresh. Manual Refresh and resume events during mutation set the existing `pendingEmailRefresh` flag and coalesce to one follow-up refresh after the matching mutation finishes.

All continuations, generation changes, raw checks, and state publication remain confined to `workScope` on `Dispatchers.Main.immediate`. Every mutation checks cancellation and current token/generation/caller/authorization/selected target before dispatch, after each suspension, and immediately before publication. Refresh uses the corresponding version and generation checks plus `ensureActive`. The raw target check uses `node.config.userId`, so a callback cannot exploit lagging derived eligibility. Observing `node.configState` invalidates private state and cancels obsolete jobs on live retarget; returning to the bound target starts a new generation and fresh load. Where a callback discovers a raw session mismatch before the collector runs, synchronizing that mismatch through the same invalidation helper prevents an obsolete job from retaining active ownership.

Invalidation clears the private profile, raw input, email dirtiness, saved recipient, verification result/recipient, and private errors before a new generation can load. Only the generic interruption Boolean may remain outside the private section. `finishEmailMutation` releases busy/deferred refresh only for the matching active token; an old `finally` cannot affect new work. Node destruction uses the existing lifecycle cancellation. Logout retains the existing immediate `onNavigateBack` exit, including bypass of dirty confirmation. Email save itself never calls `onSaved` or changes navigation.
