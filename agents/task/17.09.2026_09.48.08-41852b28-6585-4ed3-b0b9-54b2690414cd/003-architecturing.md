## Persistence and concurrency

Add nullable `pending_email` text and nullable `email_change_allowed_at` BIGINT columns to `users`. The latter stores UTC epoch milliseconds. Keep the existing current-email and username unique indexes, and index the pending column for lookup. A pending unique index is useful defense in depth, but is not the cross-slot uniqueness mechanism. In `RegisteredUser`, append `pendingEmail: Email? = null` and `emailChangeAllowedAt: Long? = null`; keep `NewUser` unchanged, with no caller-writable approval, pending, or deadline fields.

Use a small internal Exposed table, `users_write_lock`, with integer primary key `id` and integer `marker`, and one durable row whose id is 1 and marker is 0. Initialize the table and row additively and idempotently with the users repository. Never delete or recreate the row during normal operation. Every users write transaction must first execute an UPDATE of marker to 0 on that row and require exactly one matched row, before reading any users state. PostgreSQL must use READ COMMITTED for these transactions; SQLite uses its supported serializable transaction setting, with the first database operation being the lock-row write. No prior SELECT may establish a stale SQLite snapshot. A missing lock row is an infrastructure failure, never permission to continue unlocked.

On PostgreSQL, concurrent UPDATE statements on the singleton row wait for the preceding transaction to finish. Subsequent READ COMMITTED reads therefore see preceding committed user mutations. On SQLite, the first UPDATE obtains the database writer reservation before the cross-slot query. Both engines consequently serialize the check and mutation for every participating writer. The lock is database-owned, so separate `Database`, repository, and application instances cooperate. A users-repository-only solution is appropriate because all application users mutations already pass through this seam. Direct SQL writers and old binaries do not participate and are excluded from supported live operation.

After acquiring the lock, check every newly acquired non-null address against both raw stored columns of other users, excluding the target id. Preserve existing exact string equality; do not introduce case folding or normalization. This query must use raw SQL column values, not defensively parsed model values, so malformed historical values are not rewritten or made invisible to ownership checks. Insert/create must check against pending addresses; pending replacement must check against current and pending addresses; approval must retain the candidate's ownership and atomically release the former current address. A conflict throws `DuplicateUserFieldException` before mutation. The existing classifier continues to translate actual PostgreSQL/SQLite unique violations and preserve their causes; a cross-slot precheck conflict has no fabricated SQL cause. Unrelated constraints, lock timeouts, BUSY errors, and database failures remain infrastructure failures.

Cover `create(List<NewUser>)`, single `update`, bulk `update`, dedicated email mutation, dedicated username mutation, `approveEmail`, and `deleteById(List<UserId>)`. Batch writes use one lock and one transaction; a later collision or restriction rolls back the entire batch, including earlier username changes. Sequential checks within the transaction see earlier batch writes. Address swaps need not receive special support. Missing update ids retain the existing omission/null result semantics. Do not wrap a suspending `super.create` or `super.update` inside an outer transaction: inherited code publishes flows after its own transaction, which could become a pre-commit publication when nested. Implement the small SQL bodies directly, then publish create/update/delete events only after the outer transaction commits. Approval replay emits no redundant changed event. Cancellation or notification failure after commit remains an uncertain response, recoverable by a fresh read; do not claim rollback of a committed database write.

The material tradeoff is serialization of users writes, including unrelated accounts. These are short identity mutations; SMTP and role operations stay outside the database transaction. This is the smallest common PostgreSQL/SQLite implementation that does not duplicate all occupied addresses into a reservation table with its own backfill, ownership, and cleanup lifecycle. A process mutex, independent unique indexes, or unlocked read-then-write queries were rejected because they cannot enforce the requested invariant. Exposed transaction retries may retry only database work; no SMTP, role grants, or flow publications may run inside a retryable body. Exhausted contention remains observable and must not become 409 or 429.

## Exact lifecycle and repository operations

Add `setEmail(id, email): RegisteredUser?` and `updateUsername(id, username): RegisteredUser?` to `WriteUsersRepo`. Extend `approveEmail` with `cooldownMillis: Long = 0`. The argument is an internal validated policy value, not an HTTP field. Implement these methods in Exposed and cache repositories and all existing UsersRepo test doubles. Do not provide an unsafe interface fallback that implements email changes by cached read plus generic update.

The Exposed repository takes an injectable `nowMillis: () -> Long`, defaulting to the server's `System.currentTimeMillis`. Sample the clock inside the write transaction after lock acquisition. All real email mutation methods enforce the persisted deadline from the locked row, so direct repository/admin entry points cannot bypass the cooldown. Equality is exact: a mutation is permitted at `nowMillis == emailChangeAllowedAt`; it is rejected only when now is smaller. Reject with the typed cooldown exception before checking whether the requested address belongs to another account, preserving generic disclosure and leaving every user field unchanged.

Before the first approval, retain existing registration semantics: the unapproved candidate is stored in `email`, `emailApproved` is false, and `pendingEmail` is null. Saving a different address changes that unapproved current candidate. After an approval exists, saving a different non-null address retains current email and approval and changes only pending email. Replacing pending B with C releases B and retains approved A. Saving the already persisted pending address is a no-op. Saving the current email is also a no-op and preserves an existing pending address; no implicit cancellation action is added. The UI treats either exact saved slot as already stored and will not offer a misleading save operation for the retained current address.

Explicit null remains the existing clear operation. If any email state would change, enforce the cooldown first, then clear current, pending, approval, and deadline together. An already empty record is a no-op. No clear button is introduced. This preserves the existing explicit API removal capability; the latest-approved retention guarantee applies to replacement requests. A same-address/no-op PUT may succeed during cooldown because it does not change an address or extend a deadline. The UI still disables Save during an active restriction.

Generic `update(id, NewUser)` changes username and delegates its email component to the same locked lifecycle semantics. When the supplied email equals the stored current address, preserve pending state and the deadline. A null email continues to mean explicit clear, not an omitted field patch. If the email component changes and is blocked, the username change rolls back too. `updateUsername` changes only username without making an email decision, so a stale UI cannot discard pending state and a cooldown does not prohibit renaming. The coordinator calls these dedicated operations directly instead of constructing `NewUser` from a cached record.

Approval has three accepted cases. For a matching pending address, atomically move pending into current, set approved true, clear pending, and issue a new deadline. For a matching current unapproved first address with no pending replacement, set approved true and issue the deadline. For a matching current already-approved address with no pending replacement, return the unchanged row and preserve the previous deadline, including a legacy null deadline. Every other case returns null without mutation, including an old current A link while B is pending and a B link after pending C superseded B. Deadline enforcement applies to requesting another change, not to approving the already selected candidate.

For a positive policy, compute the deadline with checked Long addition of locked server time and validated milliseconds. An arithmetic failure aborts the transaction; never wrap or silently clamp. With zero duration, record a null deadline. A configuration change affects future approval transitions only; already-issued deadlines remain in force, even when the new configuration is zero. Replaying approval with a different configured duration still does not extend or shorten the stored deadline. Clock synchronization remains a deployment responsibility for multiple processes; client clocks never authorize writes.

The coordinator retains its process-local mutex around approval and the retryable role transition. Remove the current-email-only precheck and let `approveEmail` decide exact candidate eligibility atomically. Only a non-null approved result proceeds to the existing `promoteNewUserToUser`. Role failure leaves durable approval and its original deadline intact; the same valid link retries role convergence without resetting the clock. Revoked users remain fail-closed, confirmation failure does not undo approval, and no credentials are issued. This task does not turn the existing separate role repository, in-memory auth sessions, or role caches into a distributed atomic account system. Database address ownership and deadline enforcement are cross-instance; role orchestration retains its existing process scope.

## Migration, rollout, and recovery

The forward path expands the users table through the existing `initTable` convention, creates the singleton lock table/row, and preserves every existing id, username, current email, approval value, password, role, and link payload. Old approved and old unapproved rows start with null pending/deadline. No approval time is invented or backfilled. Defensive email parsing remains; migration must not rewrite malformed legacy strings. Reopening the database only ensures schema/lock-row existence and must never reset new fields or the singleton state.

Deploy with old application writers stopped, initialize/verify the expanded schema, and start the new binary. Do not run old and new writer binaries concurrently: old code neither takes the lock nor maintains pending state, so rolling mixed-writer operation can violate ownership and retention. A newly deployed client can decode old payloads, but needs the new server for pending/cooldown behavior. Old clients can decode new private fields with the existing Json settings but cannot present the new two-address flow; an old client may report an unconfirmed replacement after receiving retained A from getMe. Deploy the UI with the server for the intended experience.

Retain a database backup before deployment. Prefer rolling forward with fixes. An old binary is not a behavior-preserving rollback after new pending/deadline data exists. An emergency old-binary recovery requires stopping writes and either restoring the pre-upgrade backup, explicitly accepting loss of post-backup writes, or separately designing a compatibility backport that honors the new state. Do not automatically collapse pending into current, delete new columns, clear deadlines, or downgrade the lock protocol. No destructive contraction is authorized by this task.

## Research adaptation and completion gate

PostgreSQL's [explicit locking documentation](https://www.postgresql.org/docs/17/explicit-locking.html) explains conflicting row UPDATE locks and waiting until transaction completion. The singleton-row protocol adapts that mechanism to the small existing UsersRepo instead of introducing a new service. The subsequent reads deliberately use READ COMMITTED; a repeatable snapshot established before acquiring the lock would not be a valid substitute.

SQLite's [transaction documentation](https://www.sqlite.org/lang_transaction.html) and [isolation documentation](https://www.sqlite.org/isolation.html) describe its single-writer model and read-to-write upgrade failures. The design makes a real lock-row UPDATE the transaction's first database access, obtaining writer ownership before lifecycle reads. Contention remains a retryable or surfaced infrastructure outcome; it is never mislabeled as an email collision. Real file-backed concurrency tests are required to validate the actual Exposed/driver behavior.

[RFC 6585, section 4](https://www.rfc-editor.org/rfc/rfc6585.html#section-4) defines 429 and permits Retry-After. The application returns a typed absolute deadline on its authenticated owner mutation route, retaining existing 409 meaning and avoiding a client guess based merely on status. No rolling-count quota or resend rate limit is introduced.
