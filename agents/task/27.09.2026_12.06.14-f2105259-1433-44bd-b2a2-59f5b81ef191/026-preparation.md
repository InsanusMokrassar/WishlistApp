## Research and adaptation

Native web research was performed on 2026-10-02 before finalizing this recommendation. Primary sources consulted:

- [Martin Fowler, Bounded Context](https://martinfowler.com/bliki/BoundedContext.html) explains explicit model boundaries and mapping between context-specific models. Applied here, the reduced User entity, anonymous users projection, and owner-private lifecycle projection remain different models. The operator's required ownership is implemented through the users-feature module; a new service or a physical table split is unnecessary.
- [Kotlin serialization overview](https://kotlinlang.org/docs/serialization.html) describes serialization across multiplatform runtime objects and wire formats. The move remains in commonMain, using the existing kotlinx.serialization and MicroUtils conventions rather than introducing a platform-only DTO or mapper framework.
- [Kotlin `ignoreUnknownKeys`](https://kotlinlang.org/api/kotlinx.serialization/kotlinx-serialization-json/kotlinx.serialization.json/-json-builder/ignore-unknown-keys.html) documents that unknown properties fail by default and are ignored when explicitly configured. Therefore preserve the existing reduced-model compatibility tests under the intentional permissive Json fixture; do not silently broaden global decoding or claim that a missing pending field can be reconstructed from identity payloads.
- [Kotlin `encodeDefaults`](https://kotlinlang.org/api/kotlinx.serialization/kotlinx-serialization-json/kotlinx.serialization.json/-json-builder/encode-defaults.html) documents default omission and distinguishes encoding from decoding. Exact descriptor keys and explicit-default encoding should be tested separately from populated payload keys, so default/null fixtures cannot hide accidental ownership fields.
- [Exposed transaction documentation](https://www.jetbrains.com/help/exposed/transactions.html) places CRUD inside transactions. Preserve the repository's existing locked transaction and post-commit publication; moving a Kotlin model does not justify extracting lifecycle columns into a separate transaction or repository that weakens atomicity.
- [Korlibs date documentation](https://github.com/korlibs/docs.korge.org/blob/main/time/dates.md) describes DateTime as a UTC instant backed by Double. Retain the repository's explicitly narrower integral ±2^52 millisecond domain and checked storage conversions. The documentation does not establish a reason to enlarge the accepted range or revive Long application timestamps for this ownership correction.

The current public Kotlin API documentation identifies a newer serialization documentation version than the repository may use. The cited behaviors are stable concepts, not an instruction to upgrade dependencies or adopt newer annotations. An attempted raw GitHub fetch of the latest MicroUtils serializer returned a cache miss; no dependency-upgrade or latest-source claim relies on that fetch. Current repository annotations and existing compatibility tests are sufficient evidence for preserving the already-established serializer contract.

## Alternatives and decision

Keeping EmailProfile in email/common preserves the clean User model but fails the explicit users-feature ownership in R1. Adding pending fields to public UsersFeatureUser would satisfy a superficial naming interpretation but disclose private candidate addresses through an anonymous endpoint and violate established behavior in R2. Extending User/RegisteredUser again directly contradicts the operator's separation request. Introducing another private users endpoint or another wrapper snapshot duplicates a functioning transport or model without necessity. Moving only pendingEmail while leaving requested-at/deadline in another snapshot splits one atomic lifecycle and risks incoherent reads. Physically moving lifecycle columns to a new table and repository introduces a migration and changes cross-slot transaction behavior without an ownership requirement for physical storage. All are rejected in favor of relocating the existing coherent external projection.

Renaming the model to `UsersFeatureEmailProfile` would make feature ownership visible in the simple type name, but module/package ownership already establishes the boundary. Keeping EmailProfile reduces unnecessary source churn and preserves existing terminology. This is a council design choice, not a new operator preference requiring clarification. Old-package source compatibility cannot be maintained by a typealias inside email/common without a dependency cycle; matching source modules are rebuilt together.
