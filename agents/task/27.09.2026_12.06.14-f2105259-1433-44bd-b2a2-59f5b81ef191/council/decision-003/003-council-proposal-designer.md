## Concrete policy recommendation and alternatives

Adopt finite integral epoch-millisecond instants within inclusive `[-4503599627370496, 4503599627370496]` for durable email lifecycle values. The bound follows the pinned DateTime lossless range supplied in the brief. Validate raw database Long values before conversion, and validate DateTime values before conversion to storage. Validate deadline arithmetic before committing; neither rounding, saturation, wrapping, clearing nor replacement with the current time is acceptable. Keep storage columns unchanged. Application clocks and state use DateTime; Long conversion exists only at checked persistence boundaries. IDs and duration arguments retain their existing types.

Use MicroUtils DateTimeSerializer directly for serializable DateTime properties, retaining wire property names and nullable defaults. Reject invalid email lifecycle values through model or boundary validation without replacing the required serializer. A malformed 429 must follow the existing generic storage-failure path; it must never produce a trustworthy-looking cooldown or positive saved confirmation. A failed owner-profile decode stays a failed refresh, not an empty profile. Invalid stored timestamps fail the affected lifecycle read or operation without rewriting the row, publishing events, or inventing a 429/409 business classification. Existing generic error/recovery UI remains sufficient; unsupported persisted data requires operator repair or rollback, not repeated user edits.

Arithmetic must preserve positive-duration ceiling semantics. In particular, adding a very large accepted duration must not first round through Double and accidentally land inside the accepted range. A checked integral boundary calculation is acceptable even though application instants themselves are DateTime. Invalid clock samples or out-of-range sums fail before mutation. Zero cooldown continues to create no new deadline; idempotent approval must not acquire a new timestamp or fail merely because an unused clock is invalid.

Compared alternatives: accepting arbitrary Long-to-Double conversion silently changes deadlines and snapshot identity; reject it. Saturating or clearing extreme deadlines changes permission and recovery outcomes; reject it. Maintaining an extra Long representation or custom serializer preserves more legacy cases but conflicts with the requested application type/serializer and expands scope; reject it. Restricting timestamps to current business dates is feasible but introduces an arbitrary narrower policy absent product requirements; prefer the library's stated exact range. Supporting every integral Double beyond that range provides irregular representability and weakens a simple cross-platform contract; reject that complexity.

The proposed range is deliberately narrower than JSON's interoperable integer guidance. RFC 8259 section 6 describes interoperable integers up to the binary64 exact-integer limit; it does not guarantee compatibility with consumers that require integer lexical tokens. MicroUtils Double output may include a decimal point or exponent. Preserve old integer input within the accepted range, but do not claim old Long decoders accept the new output. Deploy matching clients/server together and invalidate cached web assets. Source: [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259).

Before deployment, with writers stopped, perform a read-only check of both lifecycle columns for non-null values outside the accepted interval, recording counts and the affected row identifiers in restricted operator output. A nonzero result blocks this rollout until a separately authorized repair or compatible recovery path is prepared; never rewrite or discard values automatically. Runtime checks remain necessary after preflight. The type migration adds no database contraction, but it also does not cancel existing lifecycle rollout restrictions. Preserve the existing backup/restore and compatible-backport recovery guidance, including post-backup loss disclosure.
