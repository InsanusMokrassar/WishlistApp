## Concrete policy and alternatives

Recommend finite integral epoch milliseconds in the inclusive range [-4503599627370496, 4503599627370496] for durable email request times and deadlines. Preserve nullable BIGINT columns and null legacy history. Check raw database Long bounds before constructing DateTime, and check finite, integral and range validity before any DateTime-to-Long write. Never clamp, truncate, clear, restamp or rewrite unsupported existing rows. Reject affected private reads and lifecycle mutations with an infrastructure/data-integrity failure; do not disguise the error as duplicate 409, cooldown 429, missing-account 404, or unrestricted null. Public reduced user reads need not materialize private timestamps and should remain available. Unrelated username-only operations should not acquire a new dependency on parsing private timestamps.

Use DateTime for clocks, models, exception payloads, UI state/snapshots and instant parameters. Keep Long only at the SQL boundary, during checked boundary arithmetic, and for durations/counters/IDs. Validate the server clock at its use point. Preserve the existing whole-millisecond production clock contract; any intentional fractional clock normalization belongs only in the production clock adapter, never in the general persisted-value conversion. Tests supplying an invalid fractional DateTime must fail rather than silently truncate it.

Calculate approval deadlines with checked integral boundary arithmetic and validate the resulting range before SQL mutation. Validate duration representability at startup and again against the actual post-lock clock when issuing a deadline, since startup cannot guarantee a future result. A checked Long addition at this boundary is compatible with an application DateTime rule. Zero policy still means no deadline; replay of already-approved exact email remains a no-op and does not need a new clock sample. Invalid state must not commit a partial row or publish cache/repository events. Existing illegal-argument configuration failures and infrastructure failure handling should remain distinct from ordinary domain outcomes.

Use MicroUtils DateTimeSerializer directly on serialized instant properties. Preserve keys, defaults and nullability, including fetchedAtMillis despite its legacy name. Legacy integer JSON input is supported for representable values; output uses Double numbers and may include fractional notation or exponent spelling. Do not claim old Long decoders accept that output. Validate email profile/cooldown model values at their semantic boundary so malformed DateTime values cannot masquerade as authoritative UI restrictions. Since decodeDouble already rounds excessive numeric precision, this policy guarantees the representability of decoded values, not arbitrary source-lexeme precision. Server-owned timestamps are not accepted in mutation request bodies. A custom exact-lexeme serializer is unnecessary scope expansion.

Keeping arbitrary Long identity with an auxiliary raw value or custom serializer would preserve extremes but contradict the requested application type/serializer contract and multiply sources of truth. Blind Double conversion is simpler but can silently change deadline order and collapse feedback identity. Clamping, treating invalid values as null, or auto-repairing rows can shorten restrictions or falsify history. Expanding to the largest exactly representable binary64 integers would exceed the library's documented safe domain without a product benefit. Rejecting unsupported values is the preferred explicit compatibility change.

Before deployment, run a read-only count of non-null values outside the chosen bounds in each of the two users timestamp columns; return counts, not mailbox values or row dumps. Nonzero counts block this rollout pending explicit data remediation or compatible backport, without automatic writes. Take and verify the existing required backup, stop old writers, deploy matching server/UI and invalidate stale web assets. Keep BIGINT schema intact. A DateTime-only rollback must still obey the branch's existing lifecycle rollback restrictions; no assertion of universally safe binary downgrade is justified. Forward repair or the documented compatible backport/backup restore remains the recovery path.
