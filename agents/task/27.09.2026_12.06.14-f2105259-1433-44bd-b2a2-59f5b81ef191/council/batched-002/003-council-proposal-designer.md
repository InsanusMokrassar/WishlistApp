## Recommendations and risks

DES-01, required for AC2: preserve the complete owner journey. Keep approved current email visible while a replacement is pending. Preserve null requested-at for unknown legacy history; never substitute the epoch or current time. Requested-at remains feedback identity, not a restriction deadline or a new rendered control. A deadline blocks mutation strictly before the instant; equality allows mutation. Save and captured IME callbacks must use the same DateTime comparison. Refresh remains usable during a cooldown. Retargeting, logout, and loss of ownership must continue removing all private feedback and pending work. No new strings, widgets, or localization behavior are needed.

DES-02, required for AC2: explicitly document numeric-wire compatibility. Applying the required MicroUtils serializer can emit floating-point JSON numbers where Long previously emitted integer numbers. Preserve JSON field names, including the existing fetchedAtMillis key if the Kotlin property is renamed to fetchedAt. Confirm new consumers can read legacy integer payloads and that null/default omission behavior is unchanged. Do not claim old Long consumers can decode new decimal-form payloads without evidence. Existing email/users rollout documentation already requires matching server/UI versions and invalidation of old web assets; update that explanation to mention the timestamp wire representation. Preserve that existing coordinated rollout contract rather than adding dual-format transport or a custom serializer without a requirement.

DES-03, required for AC2: preserve observable precision and failure classification. DateTime has Double-based milliseconds, so conversion does not preserve every possible Long instant. Establish representable range and duration-addition behavior in the candidate, including existing overflow tests. Ordinary persisted modern timestamps must retain millisecond identity; a one-millisecond requested-at change must still withdraw stale positive feedback. Malformed cooldown bodies must remain ordinary failure feedback rather than turning into an authoritative restriction, successful save, or raw numeric display. Non-finite values and unsupported extremes require an explicit implementation/test decision; silent precision loss should not be called unchanged behavior.

DES-04, required for AC2: retain storage continuity and cache/upload behavior. Existing nullable BIGINT timestamps can remain raw boundary encodings if converted immediately into DateTime application values, with unchanged column names, units, and null meaning. This avoids a new data migration merely to change a Kotlin type. Currency refresh must keep last-good fallback during upstream failure, and unfinalized uploads must retain the same expiry threshold. No countdown, local-time formatting, rate-age widget, or upload UI is implied.

DES-05, required for AC3: publish a concise project-wide convention in accessible project documentation: all application moments use korlibs.time.DateTime; serializable moments use the MicroUtils DateTimeSerializer; durations, counters, IDs, and explicit database/protocol encodings are separate concepts. Root README architecture guidance can hold the global rule without requiring participants to inspect forbidden ordinary instruction files. Update email model and architecture descriptions from Long timestamps to nullable DateTime, clarify numeric serialization and unchanged lifecycle meaning, update users storage-boundary notes, state typed clock/deadline handling in UI/users Architecture Notes, replace the currency unixMillisLong caching explanation, and identify DateTime first-seen tracking in files Architecture Notes. Preserve all Operator Notes and existing recovery guidance.

## Alternatives, assumptions, and questions

A full SQL timestamp migration adds operational risk without a stated need and is not recommended. An ISO date string serializer conflicts with the requested supplied MicroUtils serializer. A UI countdown or timezone redesign expands scope and is not recommended. Renaming internal fields to remove a Millis suffix is reasonable when the serialized field name remains stable.

Assumption: the documented coordinated server/UI rollout remains the deployment contract. Confidence is high for UI behavior and timestamp inventory, moderate for pinned-library numeric edge cases pending exact dependency verification. No operator questions are currently necessary; representable-range and pinned-artifact details are technical evidence gaps for the candidate to resolve. If preserving arbitrary Long extremes proves necessary but incompatible with DateTime, request an explicit operator decision instead of silently narrowing the contract.
