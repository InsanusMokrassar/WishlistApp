## Recommendations and issue dispositions

SEC-01 — Open design requirement for AC2: preserve representability and fail-closed deadline issuance. DateTime's Double representation cannot exactly preserve every Long millisecond value. A mechanical replacement of Math.addExact with unchecked floating-point date addition can remove the existing rollback-on-overflow protection or round a positive cooldown to no increase. The current regression is approvalDeadlineOverflowRollsBackWithoutPublishingAnEvent in ExposedUsersRepoSqliteTest.kt:1227. Define the accepted durable timestamp domain explicitly, validate finite values and lossless integral-millisecond conversions at persistence boundaries, and retain checked addition before approval writes. Do not silently clamp invalid values or convert invalid persisted deadlines to null. If a stored timestamp cannot be represented under the chosen contract, report failure without rewriting or discarding the raw row. A conservative contiguous integral domain within Double's exact integer range is feasible; precision checks should remain local to timestamp persistence and issuance. Preserve rounding positive fractional cooldown durations upward. The candidate must specify how the existing extreme-clock test changes under the new domain, rather than simply deleting the test.

SEC-02 — Open design requirement for AC2: preserve storage shape and explicitly declare wire compatibility. Keep the nullable BIGINT epoch-millisecond columns and their names, mapping at the database boundary to DateTime. Do not migrate those columns to a SQL local timestamp or floating-point storage merely to change the Kotlin type. Apply MicroUtils DateTimeSerializer directly to serialized DateTime properties, including nullable fields, and verify the resolved annotation pattern compiles. Numeric JSON remains epoch milliseconds, but a Double serializer can emit decimal/exponent forms that an older Long decoder may reject. New code accepting old integer JSON does not establish compatibility in the opposite direction. Retain JSON field names, including fetchedAtMillis if the Kotlin currency property is renamed via SerialName. Document coordinated server, web, desktop, and Android updates as necessary unless compatibility tests prove a broader guarantee. Existing email rollout notes already prohibit mixed incompatible versions; extend the explanation to changed currency/email timestamp encodings. Do not substitute a homegrown Long serializer for the requested MicroUtils serializer to conceal the compatibility difference.

SEC-03 — Open acceptance requirement for AC2: preserve authority and privacy. Server clocks remain authoritative and sampled after the durable write lock; UI DateTime comparisons remain advisory. Equality with the deadline must permit mutation. A rejected write must leave candidate, current approved email, request time, deadline, username and emitted events unchanged as currently required by transaction tests. Requested-at remains lifecycle history, never proof of ownership, a generation token, expiry, or a resend limiter. Preserve exact-candidate approval and idempotent replay, bearer-owner lookup, private profile projections, and UI owner-generation checks. Changing the type must not move private timestamps into auth, public user, or admin list models. Keep the existing 429 versus 409 distinction.

SEC-04 — Open acceptance requirement for AC2: retain cache and cleanup boundaries. Convert actual fetched/first-seen instants and clocks to DateTime; keep TTL and sweep intervals as durations or existing millisecond duration counts. Preserve cache validity only while elapsed time is strictly less than TTL and upload deletion at elapsed time greater than or equal to TTL. Keep mutex ownership and delete-only-after-removal behavior. A completed upload absent from the temporal map must not have its permanent file deleted. Preserve last-good currency fallback on provider failure. Do not introduce an unrelated upload authentication or rate-limit change.

SEC-05 — Nonblocking documentation recommendation for AC3: put the public project-wide rule in root README Architecture and describe DateTime, MicroUtils DateTimeSerializer, UTC epoch-millisecond boundaries, nullable legacy timestamps, and exclusions for durations, identifiers, counters and monotonic elapsed-time measurements. Update Architecture Notes in features/email/README.md, features/users/README.md, features/ui/users/README.md, features/currency/README.md, and features/files/README.md. Preserve every Operator Notes section and existing ownership and recovery rules. Instruction-file edits are outside my permitted inspection; a public README rule satisfies my security perspective without relying on an unread instruction file.

## Alternatives, assumptions and exclusions

The preferred design preserves BIGINT storage and uses typed application instants with explicit boundary conversion. Converting storage to SQL timestamp types adds timezone and migration risk without satisfying an additional requirement. Keeping application Long timestamps behind type aliases would not satisfy the requested type conversion. A custom integer DateTime serializer conflicts with the explicit MicroUtils serializer requirement. Retaining existing wire property names with SerialName permits cleaner Kotlin names without gratuitous JSON schema changes.

Confidence is high in the identified security boundaries and pinned serializer behavior. Exact annotation syntax, DateTime arithmetic helpers, and the final inventory across all test fixtures still need the implementation plan's concrete selection and compile verification. Existing wall-clock adjustment behavior remains unchanged; replacing security timers with a monotonic-time subsystem is outside this task. No new secret handling, permissions, authentication mechanisms, destructive migrations or data repair is proposed.

Operator questions: none are currently necessary. A conservative checked timestamp domain, unchanged raw storage, and the documented coordinated rollout provide a feasible plan. If a candidate instead claims lossless support for every historic Long value or mixed-version old-client compatibility, that claim requires evidence or an explicit revised compatibility decision before acceptance.
