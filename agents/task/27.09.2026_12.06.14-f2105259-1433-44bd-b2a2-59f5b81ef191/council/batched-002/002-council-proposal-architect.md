## Compatibility, alternatives and risks

MicroUtils produces floating-point JSON numbers, potentially decimal or exponent lexical forms. Preserve existing field names and verify decoding legacy integral JSON, but do not claim old Long-based readers accept the new representation. Follow the already documented coordinated server/UI rollout and invalidate old web assets; existing README deployment constraints already rule out mixed incompatible writers. The requested serializer choice determines numeric representation, so changing to ISO text or writing a local Long serializer would contradict the request.

BIGINT storage keeps ordinary existing values and nulls unchanged, avoiding timezone and database-driver migrations. A SQL timestamp column, JSON persistence for lifecycle fields, or wholesale repository transform is unnecessary. Keeping Long domain fields with conversion only at rendering fails R2. Converting TTLs, IDs, counters or monotonic elapsed markers into DateTime would confuse distinct quantities and is excluded.

The timestamp refactor adds no schema migration of its own. Rollback of this refactor alone can reuse ordinary BIGINT values, but cannot waive the PR's pre-existing coordinated deployment and lifecycle rollback limitations. No automatic rollback, data deletion or production deployment is part of preparation.

## Questions, issue disposition and confidence

ARCH-1 is OPEN and blocks final architectural acceptance under R2's behavior-preservation requirement. What representability policy should replace the full-Long email timestamp behavior when adopting Double-backed DateTime: may durable email instants and issued deadlines be restricted to finite integral milliseconds within the library-documented lossless range [-2^52, +2^52], rejecting out-of-range stored values and configurations instead of rounding them, or must another existing-data policy be supported? The recommended choice is the explicit lossless range with fail-closed rejection and a pre-deployment read-only data check. Evidence is the pinned DateTime source, the pinned MicroUtils serializer and the existing Long.MAX_VALUE overflow regression. The operator's answer is necessary because a new hard range changes accepted inputs and potential legacy-row handling; silent precision loss is not an acceptable default. If out-of-range production data must remain usable, obtain its required semantics before choosing a migration or exception.

No other operator questions remain. API property naming is intentionally preserved, BIGINT storage is preserved, and coordinated rollout is already required by repository documentation. All planned behavior can be covered by automated tests. Confidence is high in the inventory and ordinary-date conversion, and conditional in extreme-date compatibility until ARCH-1 is resolved. This is a design proposal with an explicit blocker, not consent to implement an unresolved precision policy.
