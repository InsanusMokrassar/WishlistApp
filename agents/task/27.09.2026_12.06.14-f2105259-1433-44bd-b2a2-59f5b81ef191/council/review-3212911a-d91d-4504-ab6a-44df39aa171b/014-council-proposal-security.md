## Security invariants, alternatives and risk dispositions

SEC-01 / AC1+AC2: UsersFeatureEmailProfile is users-feature external state, while public UsersFeatureUser retains exactly id/username. The potential failure is anonymously enumerating pending replacement mailboxes after mechanically adding the state to the existing list DTO. The feasible mitigation is the dedicated owner-only users projection and unchanged bearer-scoped route. This is a required design invariant, not a request to create a public pending field.

SEC-02 / AC2: Preserve the separation between allowed write inputs and lifecycle output. SetEmailRequest may select email or explicit clear; NewUser never supplies approval, pending state or lifecycle instants. Otherwise forged profile fields could self-approve or remove a cooldown. Keep existing request DTOs and exact-candidate repository approval. Authentication derives owner identity even when hostile userId/callerId/rootId fields appear in query/body.

SEC-03 / AC2+AC3: Model relocation must not replace fresh reads with cached User/auth/public projections or treat an invalid profile as an empty account. Either error could publish stale pending data or admit operations without an authoritative deadline. Retain mandatory getEmailProfileFresh, exact snapshot validation and fail-closed client decode.

SEC-04 / AC2+AC3: Preserve stored-range and clock validation, post-lock sampling, cross-slot uniqueness and post-commit event behavior. Existing timestamp policy is finite whole milliseconds within inclusive ±4503599627370496, with checked raw BIGINT conversion and no automatic data repair. EmailTimestamp.kt:13-68 and ExposedUsersRepo.kt:477-488 support retaining that policy without redesign. Model relocation gives no evidence requiring a new range policy. Counts-only scans, coordinated deployment and compatible recovery remain as documented; unsupported stored instants must not be rounded, cleared, restamped or reported with mailbox/row identity.

Keeping the existing EmailProfile in email/common is the lowest textual churn but fails AC1's explicit users-feature ownership. Adding pending state to public UsersFeatureUser fails the established privacy invariant. A parallel DTO with adapters leaves two owners and creates a state-dropping conversion risk. Moving storage to a new table or introducing a new users endpoint is unnecessary for this correction and expands transaction/authorization scope. The recommended canonical users-owned owner projection preserves the current wire contract and physical lifecycle implementation.

Residual risks retained from current behavior: the process-local coordinator is not a cross-process role transaction; the durable singleton users lock serializes participating writers; old/direct SQL writers that bypass the lock remain unsupported; resend has no separate rate limit; a lost Boolean PUT response can be uncertain; same-owner credential epochs are not observable in the existing UI model. No new rate limiter, reauthentication flow, role store, storage redesign or timestamp migration is proposed. These are scope limits, not grounds to reject the focused correction.
