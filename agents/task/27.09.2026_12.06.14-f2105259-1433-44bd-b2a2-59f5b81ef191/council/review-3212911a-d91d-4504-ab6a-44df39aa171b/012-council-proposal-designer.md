## Alternatives, risks and exclusions

Leaving EmailProfile in email/common is the smallest code change but fails the users-feature ownership boundary in R1. Adding pending fields to UsersFeatureUser is unacceptable: `features/users/common/src/commonMain/kotlin/models/UsersFeatureUser.kt:14` states that anonymous callers receive every field; its serializer and public service tests require id/username only. Adding the lifecycle back to AuthFeatureUser or RegisteredUser would recreate the rejected coupling and fail the stated separation. Duplicating a users wrapper and email-owned lifecycle model introduces competing snapshots and avoidable mapping risk. A separate users-owned EmailProfile preserves one canonical external snapshot.

A name such as UsersFeatureEmailProfile would make ownership more obvious, but it adds naming churn without changing this design. Retaining EmailProfile and changing its package is my recommendation. A UserId-typed wire field is likewise unnecessary scope: retain the current Long owner field and exact JSON shape.

The main risks are a dependency cycle, missed consumer imports, unnoticed serializer shape changes, lifecycle reconstruction from identity fields, privacy leakage through the public listing, and loss of request-time feedback identity. The acceptance tests below directly cover these risks. Kotlin source/package compatibility changes for callers importing the old model are real; update every repository consumer in the same change. No backward alias should pull users/common into email/common. Known external consumer inventory is unavailable; do not claim published library import compatibility.

This proposal does not add reauthentication screens, notifications to the old address, cancellation controls, resend limits, timers, timestamp widgets, accessibility framework dependencies or new browser/device automation infrastructure. Those would change the established journey beyond this ownership correction. Preserve existing roles, avatar, username/password and logout behavior.

## Independent primary research

[OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html#changing-a-users-registered-email-address) recommends recording a proposed address as pending and requiring confirmation before the change completes. This supports preserving the distinction between approved current identity and a service candidate. OWASP also recommends stronger identity checks and notifications; those are broader product policies, not permission to add new flows during this correction.

[W3C WAI form notification guidance](https://www.w3.org/WAI/tutorials/forms/notifications/) recommends understandable submission feedback and errors that explain recovery. The existing storage-uncertainty/Refresh copy and distinct delivery failure are useful behaviors to retain. [W3C Understanding SC 4.1.3](https://www.w3.org/WAI/WCAG21/Understanding/status-messages) explains that displayed asynchronous status messages need programmatically determinable semantics without forcing focus. This provides a preservation check for relocated-model consumers, not a claim that current renderers satisfy every accessibility criterion. Desktop semantic existence tests do not prove browser live announcements or Android assistive-technology behavior.

[Kotlin JsonBuilder.ignoreUnknownKeys API](https://kotlinlang.org/api/kotlinx.serialization/kotlinx-serialization-json/kotlinx.serialization.json/-json-builder/ignore-unknown-keys.html) documents that unknown input fields throw by default unless tolerance is configured. Therefore preserve the actual endpoint DTO keys and configured legacy reduced-model tolerance rather than assuming package relocation permits arbitrary wire changes. The current `UsersFeatureUserTest.kt:93` explicitly constructs tolerant Json and verifies that lifecycle keys are not re-emitted. Research was performed independently with native web search/open tools; application-specific conclusions above are repository evidence or stated inference, not claims made by these sources.
