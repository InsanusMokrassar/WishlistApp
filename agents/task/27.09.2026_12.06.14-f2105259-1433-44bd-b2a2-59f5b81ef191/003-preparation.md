## Timestamp compatibility decision

Recommend finite integral durable email instants in the inclusive range -4,503,599,627,370,496 through +4,503,599,627,370,496 milliseconds. Validate raw BIGINT values before any conversion to Double; validate DateTime values before storage, publication in email models, or deadline arithmetic. Reject fractions, NaN, infinities, and values outside the range. Null remains unknown/absent and is never converted to epoch zero. This restriction is an intentional compatibility change authorized for council decision, not a claim of full Long-domain equivalence.

Full arbitrary-Long preservation would require retaining a second canonical Long representation, a custom codec, or a different temporal type. That conflicts with the requested application DateTime rule or supplied serializer and creates dual truth. Silent rounding changes candidate identity and deadline enforcement. Saturation or clearing corrupts durable policy. A wider safe-integer range could preserve more values but exceeds the pinned library's documented lossless contract. Reject all those alternatives. Use the documented inclusive range consistently, even where isolated Double values outside it happen to be exact.

Unsupported persisted rows remain byte-for-byte unchanged. An owner email-profile read or approval that needs such lifecycle values fails as a data-integrity error; a changing email mutation validates both non-null lifecycle columns before changing or clearing anything and fails without any write or event. Username-only changes, public reduced-user reads, same-candidate no-op writes, and deletion may continue when they do not materialize or modify unsupported lifecycle values. No implicit repair or timestamp restamping occurs. This distinction limits the failure to the operations that need valid lifecycle instants.

Invalid injected application instants, invalid decoded email model instants, and an unrepresentable proposed deadline are argument/arithmetic validation failures, never cooldown or duplicate-email failures. Unsupported stored values raise IllegalStateException with a non-sensitive field-oriented diagnostic; do not include addresses or whole rows. These failures must not be mapped to typed 429 or duplicate 409. Existing uncaught server failure behavior remains applicable; client malformed-body behavior remains generic. No new HTTP error model is needed.
