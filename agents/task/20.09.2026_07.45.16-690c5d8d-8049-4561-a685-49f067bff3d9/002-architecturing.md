## Architecture decision

Use a dedicated `:wishlist.browserTests` JVM module with JUnit 5 and pinned Playwright Java. Register it in `settings.gradle` at `browserTests/`; add `browserTests/build.gradle`, `browserTests/src/test/kotlin/.../ServedWebSmokeTest.kt`, and a small `browserTests/src/test/kotlin/.../BrowserFixture.kt`. Add `playwright` and `junit-jupiter` version/catalog entries to `gradle/libs.versions.toml`. The test module depends on no production project classes: it drives only the served application. The public gate is `./gradlew browserTest`, registered by root `browser-tests.gradle` and applied after `extensions.gradle` in root `build.gradle`. Keep the script at the root because the gate coordinates client build, server runtime, browser provisioning, and process lifecycle. Use `browserTests:test` as the actual Gradle `Test` task, invoked only through the gate; disable its direct execution with a clear error when the gate's generated base URL is absent.

Wire task dependencies as `browserTest` → `:wishlist.browserTests:test` → `installBrowserChromium`, `:wishlist.server:classes`, and `:wishlist.client:jsBrowserDevelopmentExecutableDistribution`. `installBrowserChromium` is a dedicated `JavaExec` using `browserTests` test runtime classpath and `com.microsoft.playwright.CLI install chromium`; run its action only when a version-matched executable is absent. Prefer a small JVM probe using `Playwright.create().chromium().executablePath()` and a launch check for the headless shell to avoid a stale or partial install. On a failed probe, invoke the pinned CLI installer and rerun the probe; surface a clear OS-library/install error. Keep every probe and install in task execution, never Gradle configuration. Do not use `--with-deps` in the Gradle gate because that can require administrator privileges: document Ubuntu packages / `install-deps chromium` as a supported-platform prerequisite and install those packages in CI. This leaves the single Gradle command sufficient on a supported runner with OS prerequisites already present.

Start the server in `browserTests:test.doFirst` using `ProcessBuilder` and the `:wishlist.server` runtime classpath with main class `dev.inmo.micro_utils.startup.launcher.MainKt`; use the Java executable from the configured Gradle toolchain, pass the generated config's absolute path as first argument, and set working directory to the fresh temporary suite directory. Avoid `:wishlist.server:run`: its Gradle task blocks and its default config path is unsuitable for isolation. Reserve an ephemeral loopback port, write the JSON, and start promptly; a failed bind is a failing gate, not a retry against port 8196. Poll `GET /` until HTTP 200 and the expected HTML shell marker with a fixed timeout while also checking that the process is alive. Set `browser.baseUrl`, `browser.artifactsDir`, and `browser.headed` as test JVM system properties. The server process handle and temporary directory belong to a shared Gradle build service or task state owned by this gate. A `finalizedBy` cleanup task must stop descendants then the server, await bounded termination, force-kill survivors, and remove only the generated directory. Also register a build-finished shutdown hook for interruption. Preserve `browserTests/build/artifacts/<invocation>/server.log` independently of disposable state, at least on failure. Do not make the `Test` task up-to-date: each invocation needs a fresh process and database.

Generate config from a checked-in test-only JSON template or a Groovy map, retaining the `server/dev.config.json` plugin list required for the current UI, but setting `host` and `publicHost` to `127.0.0.1`, the reserved port and `publicHttpOrigin`, `staticFolders[""]` to the absolute built Web distribution, `database.url` to `jdbc:sqlite:<absolute-temp-path>/browser.db`, `database.driver` to `org.sqlite.JDBC`, `filesFolder` to an absolute temp uploads path, `enableRegistration=true`, `requireEmailForRegistration=false`, and no SMTP configuration. Keep exchange-rate credentials unset; make smoke tests avoid network-dependent currency behavior. Never load `server/dev.config.json` at runtime or infer any path relative to `server/src`. The server's `DatabaseConfig` otherwise defaults to the PostgreSQL driver even for a SQLite URL, so the explicit driver is required.

The initial suite contains two sequential Chromium tests, each with its own browser context. First navigate to `/` and assert visible `.app`, `.topbar`, and a meaningful wishlist screen or empty state after Compose has mounted, proving more than `index.html` delivery. Second register through the top-bar Register button and `#auth-username` / `#auth-password`, leave optional email blank, submit, wait for Log out, and assert an authenticated UI surface (for example the wishlist creation control, with its exact locator confirmed in Coding). Use a unique account name per invocation; no operator account is involved. Attach `page.onPageError` and `page.onConsoleMessage` listeners before navigation and fail on unexpected errors; allow only a documented, narrowly matched benign browser message if one is observed. Use Playwright locators with bounded assertions instead of sleeps. Start tracing before navigation, write a screenshot and trace ZIP on any assertion or browser failure, and retain artifacts under `browserTests/build/artifacts/<invocation>/<test-name>/`. Default to headless; `./gradlew browserTest -PbrowserHeaded=true` enables headed inspection. Do not parallelize these tests while the one server fixture is shared.

The CI workflow `.github/workflows/build.yml` should run `./gradlew build` and the exact documented `./gradlew browserTest` on Ubuntu with JDK 17 and Playwright Chromium OS dependencies provisioned before the latter. Upload `browserTests/build/artifacts/**` when the gate fails. The root `README.md` should document supported Ubuntu/JDK 17 baseline, package prerequisite, the one-command gate, headed invocation, isolated SQLite behavior, and screenshot/trace/server-log locations. `agents/VERIFICATION.md` should require this gate for Web UI or Web-affecting API/server edits alongside existing build/KMP checks; report exact command and exit code, Chromium version and number of tests, artifacts and setup limitations, or a reason it is not applicable. A required gate that cannot run or fails is FAIL; `jsBrowserTest` covers Kotlin/JS unit behavior and cannot substitute for the served-app test.

## Test specifications and stubs

`BrowserFixture` / suite setup: Given valid `browser.baseUrl` and `browser.artifactsDir`, create Playwright and launch managed Chromium on the same test thread; create a new context per test; close context/browser/Playwright in reverse order. Missing properties must fail before navigation with an actionable message. With `browser.headed=true`, launch headed; default/false launches headless. On a thrown assertion or page error, save screenshot and trace once, then rethrow the original failure. Artifact-writing failure must be reported without hiding the original assertion. Test context isolation by verifying a newly created context has no authenticated session.

`ServedWebSmokeTest.rendersApplication`: Given a ready base URL, navigate to `/`; expect HTTP success, visible Compose `.app` and `.topbar`, and visible wishlist content after bounded waiting. An HTML shell with `#content` but no mounted UI must fail. Any uncaught page exception or unexpected console error must fail and yield screenshot plus trace. Use a listener attached before `navigate`.

`ServedWebSmokeTest.registersAndReachesAuthenticatedUi`: Given the disposable database and optional-email registration, click Register, fill a generated non-root username and password, leave email blank, submit, and expect Log out and the authenticated wishlist control. A registration error, remaining logged-out state, or missing control must fail with artifacts. Do not print the password in logs or embed a fixed production-like credential.

`installBrowserChromium` / browser probe: First invocation with empty browser cache installs pinned Chromium and can launch it; second invocation with cache present skips download/install and launches it; partial cache triggers repair; missing OS shared libraries produce an actionable failure and nonzero gate. An unrelated `./gradlew help` must not run a browser probe or install.

`browserTests:test` server fixture: Given a free port and generated config, serves `/` from the built bundle and writes `browser.db` and uploads only under its temp directory. Given an occupied port or early process exit, fail within the readiness deadline, preserve server log, and cleanup. Given a browser assertion failure, stop server and descendants, remove only temp state, and retain artifacts. A second run must start with a new empty SQLite database and port. Record metadata/hash of `server/src` SQLite files before and after the gate; values must match.

## Research and project adaptation

Playwright's [Java test-runner guide](https://playwright.dev/java/docs/test-runners) shows a Gradle `JavaExec` CLI task, JUnit tests, and one context per test; the design uses those APIs in the project's Groovy Gradle structure. Its [browser guide](https://playwright.dev/java/docs/browsers) specifies revision-matched binaries and Chromium installation, so the catalog pins the Java dependency and the bootstrap runs that dependency's CLI. Its [CI guidance](https://playwright.dev/java/docs/ci) covers Linux system dependencies; those are handled explicitly in Ubuntu CI rather than requiring a privileged local Gradle task. The [tracing guide](https://playwright.dev/java/docs/trace-viewer-intro) supplies `BrowserContext.tracing()` with screenshots/snapshots; tests retain ZIPs on failure. [Gradle finalizer guidance](https://docs.gradle.org/current/userguide/controlling_task_execution.html) supports teardown after a failed test task. These practices fit the existing server launcher and `extensions.gradle` root-script pattern without a separate Node test project or ChromeDriver.
