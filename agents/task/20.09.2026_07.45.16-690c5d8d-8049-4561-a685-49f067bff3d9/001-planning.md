## Repository findings

The project is a Groovy Gradle multiplatform build. `build.gradle` applies `extensions.gradle`; `settings.gradle` names server module `:wishlist.server` and Web module `:wishlist.client`; `gradle/libs.versions.toml` owns dependency versions. `client/build.gradle` defines a JS executable, and `server/build.gradle` makes its ordinary `run` depend on `:wishlist.client:jsBrowserDevelopmentExecutableDistribution`. `features/common/server/src/jvmMain/kotlin/JVMPlugin.kt` serves `Config.staticFolders` through Ktor `staticFiles`; `features/common/server/src/jvmMain/kotlin/models/Config.kt` maps the empty key to the site root. `client/src/jsMain/kotlin/ClientJSPlugin.kt` mounts the application into `#content` and starts at the wishlist view.

`server/dev.config.json` uses `jdbc:sqlite:./local.db`, `./local.uploaded_files`, port 8196, and SMTP-backed required-email registration. Those relative paths resolve in `server/`; they must never be reused by the suite. `features/common/server/src/jvmMain/kotlin/models/DatabaseConfig.kt` defaults the JDBC driver to PostgreSQL, so a generated browser config should explicitly set `driver` to `org.sqlite.JDBC`. The server already declares Xerial SQLite in `server/build.gradle`. `features/auth/server/src/jvmMain/kotlin/JVMPlugin.kt` creates a root user on an empty database with a random password, which is unsuitable as deterministic test credentials. `features/auth/README.md` documents optional-email registration and the auth API; setting `enableRegistration=true` and `requireEmailForRegistration=false` allows a uniquely named test account to be created on the isolated server. `features/ui/auth/src/jsMain/kotlin/ui/AuthView.kt` exposes the login form with stable `auth-username` and `auth-password` input IDs. The Web client initially renders the wishlist screen, and authenticated wishlist creation can establish a meaningful user path.

`.github/workflows/build.yml` currently runs only `./gradlew build` on Ubuntu. `agents/VERIFICATION.md` currently requires `build`/KMP tests but has no served-browser gate. The root `README.md` describes a PostgreSQL-oriented local run, while the actual development config is SQLite; document the browser harness separately and avoid changing production guidance beyond corrections needed for clarity. I read the relevant feature READMEs (`features/common`, `features/auth`, `features/ui/auth`, `features/wishlist`, `features/ui/wishlist`, `features/users`, and `features/ui/scaffold`); their Operator Notes contain only the template comment and impose no extra constraint.

Code navigation used `ast-index`; its default cache path was read-only in this sandbox, so I rebuilt the initial index with `XDG_CACHE_HOME=/tmp/issue85-ast-cache`. This was an index-location workaround, not an unavailable-tool fallback.

## Plan for Architecture and Coding

Define one dedicated JVM browser-test module in `settings.gradle` and its Gradle build file, with JUnit and a pinned `com.microsoft.playwright:playwright` alias/version in `gradle/libs.versions.toml`. Put setup/orchestration in `browser-tests.gradle` applied by root `build.gradle`, following `extensions.gradle`. Keep all browser install and server-process actions inside explicitly invoked task actions; normal Gradle configuration and unrelated tasks must stay inert. The public one-command gate should build `:wishlist.client:jsBrowserDevelopmentExecutableDistribution`, provision Chromium only when absent, launch the actual server with a generated config, await HTTP readiness with a bounded timeout, run JVM browser tests, and stop the entire server process on success, failure, or interruption. Choose and document a reproducible task name such as `./gradlew browserTest`; the same command must run in CI.

Generate the config and all mutable state in a fresh temporary directory for each invocation: absolute SQLite JDBC URL with explicit SQLite driver, absolute uploads directory, absolute Web bundle directory, loopback bind, an available local port, registration enabled without mandatory email, SMTP disabled, and the production plugin list required for the chosen user path. Ensure teardown removes the temporary state only after the server exits; no task should address `server/local.db`, `server/local.uploaded_files`, or operator accounts. Select a free port in the task and pass the final URL to tests; bounded readiness should verify a served page and API health before running Playwright. Preserve server logs as diagnostic artifacts if startup fails. Check whether the launcher requires a working directory or absolute config path, and use an explicit process working directory so path resolution is deterministic.

The browser smoke test should navigate to the server URL in Playwright-managed headless Chromium, wait for visible application content beyond the HTML shell, register or log in with a deterministic account on the disposable database, then exercise an authenticated UI action such as creating a wishlist and seeing it rendered. Attach page-error and console-error listeners before navigation and fail for unexpected errors. Use explicit element assertions and bounded waits, not sleeps. Each test should use a fresh context; keep the initial suite small. Capture a screenshot and Playwright trace on failed paths into a documented build artifact directory, and retain these artifacts across cleanup. Offer headed/debug mode through a Gradle property or environment setting, with headless as the CI default.

Browser bootstrap should use the pinned Playwright Java CLI or API so the dependency and browser revision agree. Detect an installed matching browser before installation, and make setup idempotent; if invoking Playwright install is itself idempotent, avoid redundant network/install attempts with an explicit existence check. Consider Linux OS dependencies: on Ubuntu CI either install documented packages in the workflow or call Playwright's supported dependency installer in a dedicated setup action. A failed prerequisite must give an actionable error and fail the gate. No global Playwright, ChromeDriver, Docker, or PostgreSQL should be required. Confirm Gradle wrapper, Playwright version, and Chromium revision on a clean checkout rather than relying on a developer cache.

Update `.github/workflows/build.yml` to run the same `./gradlew browserTest` gate after setup and publish screenshot, trace, and server-log artifacts on failure. Update root `README.md` with the single local/CI command, supported OS/JDK and optional system packages, headed/debug command, isolation statement, and artifact path. Update `agents/VERIFICATION.md` to require the browser gate for Web UI and Web-affecting API/server changes in addition to `build` and KMP tests; for unrelated changes require a reason for skipping. Require exact browser command/exit code, browser and test counts, artifact paths, and setup limitations in each step report. A failed or unavailable required browser gate must yield FAIL and return to Coding; `jsBrowserTest` cannot stand in for the served-application suite.

Architecture should inspect Gradle's existing launcher/main-class wiring and Playwright CLI behavior before settling process orchestration details. Coding should run the documented gate twice locally to prove idempotence and isolation, inspect the operator DB file's metadata before and after, and run the existing build gate. Verification should run the browser gate and record the required counts and artifacts. A clean CI run is the final proof of recoverable provisioning; if CI cannot be executed locally, do not claim that acceptance condition as verified.
