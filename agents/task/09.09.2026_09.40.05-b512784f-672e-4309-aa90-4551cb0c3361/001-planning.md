`features/email/server/src/commonMain/kotlin/Plugin.kt` registers SMTP transport only when the nested email configuration exists and is non-null. `EmailFeatureService.isFeatureEnabled()` returns true for that graph, while `DisabledEmailFeature` represents disabled delivery. A configured blank SMTP host is still a configured capability, but its delivery fails. This is the existing meaning of SMTP enabled and should remain the request-action predicate. Server eligibility must independently verify the authenticated caller's current, non-null, approved email; client visibility is never authorization.

`EmailRegistrationInviteSender.kt` demonstrates UUID minting, a validated `publicHttpOrigin`, an absolute `/api/links/{id}` URL, exact-link failure cleanup, and cancellation propagation. `EmailVerificationAccountCoordinator.kt:43` and `:100` serialize current-email mutations and exact-address verification under one mutex. SMTP deliberately runs outside that mutex. A password approval must use the same account-state boundary for final email checks; fetching a record and later writing a password without coordinated revalidation permits an intervening email change.

`features/deeplinks/server/src/commonMain/kotlin/services/DeepLinksService.kt` persists `DeepLinkHandlerInfo` under the newly minted `DeepLinkId`, dispatches by the stored handler ID, and does not expire or consume links. The approval is the existing persisted deeplink UUID, not a newly minted token after opening the link.

`features/auth/server/src/commonMain/kotlin/services/AuthFeatureService.kt:309` is the existing BCrypt password-write boundary. It hashes under the auth write lock and does not revoke sessions. The new path must reject UTF-8 input beyond 72 bytes as well as passwords shorter than eight characters; preserve existing registration and administrator behavior unless an explicitly necessary extraction is behavior-preserving. No plaintext or password hash may cross into a client-facing approval payload.

## Product and security decisions

There are no unresolved requirements requiring operator input. The Orchestrator confirmed that an authenticated owner initiates the email request, UUID authorization permits completion independently of browser login, and existing sessions remain unchanged. Opening a link in a different browser must work without issuing credentials or requiring a login. A currently logged-in account must never become the mutation target merely because that browser holds its bearer credentials. The persisted approval selects the account. If a target user ID is included in the URL or completion DTO for explicit mismatch checking, it must exactly match the stored payload; it cannot override the payload.

The handler validates the password-purpose payload and returns a fixed same-origin password-page destination containing the same UUID, encoded as a single path segment or query value. Opening the link does not change the password and does not consume the approval, allowing mail scanners and page refreshes without making the action unusable. Final submission loads and revalidates that exact persisted record. Missing, blank, malformed, unknown, consumed, expired, wrong-purpose, wrong-payload, mismatched-user, changed/cleared/unapproved-email, deleted-user, revoked-user-role, and changed-password approvals fail closed. Validate current direct User membership without promoting roles.

Use a short bounded lifetime for new password approvals; the concrete planning default is 15 minutes, matching the existing access-token default. Store an absolute expiry in the server-only payload and inject time for tests. Expiry applies to opening and submission. This is a new password-purpose policy, not a change to registration-verification links. Repeated requests may coexist until expiry or a password change; a successful password replacement invalidates previously issued approvals through the credential-state check. No latest-request registry is needed.

Successful completion is single-use under concurrent submissions. Architecture must define a serialization boundary covering authoritative reread, purpose/subject/email/credential/expiry checks, consumption, and guarded password persistence. A process-local coordinator is consistent with current deployment boundaries; do not claim distributed atomicity. Prefer consuming authorization before an uncertain password write so a storage exception cannot leave a reusable approval after a committed password change. Document that an approval consumed by a failed or uncertain storage operation requires a fresh email request. Check cancellation before entering any bounded non-cancellable commit region. Delivery cleanup removes only the exact newly minted link, also on cancellation or a stale post-send eligibility check. SMTP never runs while holding account/auth locks.

Password and confirmation stay in ViewModel memory and must match exactly without trimming. The server independently enforces password policy. A completion response does not issue credentials, switch users, or log out the browser. Success clears the password fields and retires the actionable page; normal navigation remains available. Errors never claim success and distinguish an invalid approval from retryable transport failure without exposing stored email or credential information.

## Concrete implementation plan for Architecture

First, define the shared request/result DTOs and constants, then select the smallest ownership arrangement that retains Auth ownership of password policy/hash writes and Email ownership of delivery/current-email coordination. An authenticated request should carry the displayed expected email to reject stale owner state and derive its caller solely through `getCallerUserIdOrAnswerUnauthorized()`. Completion carries the original approval UUID and new password, plus a target ID only if required for explicit subject comparison. Keep client implementations transport-only and make ordinary non-success HTTP responses or malformed response bodies fail closed. Follow existing Auth-owned server ports when dependency inversion is needed; adding an auth/server dependency on email/server would create a cycle because email/server already depends on auth/server.

Second, implement the server-only password payload, qualified handler registration, and polymorphic serializer registration. Reuse `DeepLinksService.createDeepLink` and exact-link removal. A read/consume API may be added to the deeplink service only when needed by the selected design; keep the deeplink dispatcher purpose-neutral. Avoid DI cycles in which constructing DeepLinksService collects a handler that eagerly requests that same DeepLinksService. The payload binds the immutable subject, exact approved email, expiry, and credential-state proof. Factor only the necessary public-origin URL helper from the existing sender; do not rewrite email verification or required-registration compensation.

Third, implement guarded final authorization within the existing Auth password boundary and the shared email coordinator. Establish one explicit lock order and ensure no callback reacquires an already-held non-reentrant lock. Final credential comparison and password write must share the Auth write lock; final email comparison and the authorized commit must exclude coordinator email mutation. Check stored credentials before accepting a user whose deletion is between purge and user removal. Keep the existing privileged `setPassword` semantics and direct-role checks intact. Storage-failure behavior and concurrent submission behavior must be testable with controllable repositories.

Fourth, extend `UsersModel`, its production binding, and the owner editor with a password-email request method and dedicated request result state. Derive visibility from authenticated ownership, a positively enabled SMTP capability, a matching private profile, and a non-null approved email. Use the existing owner-generation and mutation-job lifecycle; recheck ownership after suspensions and clear password-request feedback on identity invalidation. Keep the action disabled while busy or refreshing, reconcile private state after requests, and provide localized sent/failure feedback in all three views.

Fifth, add a dedicated serializable password-change config, interactor, ViewModel, localized strings, and JS/JVM/Android views in UI/users. Register its serializer and factories in existing plugins, and implement its interactor in `ClientPlugin`. The UUID must be an immutable config value submitted verbatim by the shared model; never generate, truncate, normalize, or replace it from current-user state. The page is token-authorized and must not inherit the ordinary editor's logout-exit rule. Use existing Calm Studio form components on JS and each native platform's current Material components.

Sixth, add the canonical browser route and inverse mapping, with strict segment/query validation and URL-safe encoding. Preserve the UUID through redirect, initial load, navigation serialization, and reload. Construct a fixed same-origin server redirect rather than accepting destination text from a payload or request. Remove the secret route from the active page on completion and keep the new config's log representation redacted. Update only affected feature README prose and routes, preserving every Operator Notes section.
