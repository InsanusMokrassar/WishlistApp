## Alternatives, risks, and external research

Keep the local terminal latch and existing safe users-list exit. Disabling only the button allows queued native/direct callbacks; merely retaining warning copy still permits the reviewed retry. A new persisted unknown-result route or receipt endpoint could address arbitrary reload/reopen behavior, but changes the selected scope. Browser refresh before safe exit and reopening the original email can recreate Pending; neither the report nor UI guarantee should claim otherwise.

Keep historical delivery feedback independently bound to the admitted approved recipient. Erasing Sent whenever profile temporarily becomes null recreates false-loss feedback after Refresh. Retaining result without a captured recipient cannot distinguish read recovery from authoritative address change. Showing the private companion address or persisting the companion field is unnecessary and would weaken the existing ownership boundary.

Keep immediate lifecycle-owned cleanup and committed same-record consumption. Open-time cleanup misses never-opened approvals; issuance-only cleanup misses idle installations; full getAll creates unbounded memory use. Indexed expiry metadata is a possible separate scale improvement, with schema/backfill implications outside this task. A single-process deployment restriction would require a topology/support decision and provides less robust same-approval protection than the implemented storage predicate. Joining consume and password-write into one transaction changes AC6's explicit burn-before-write choice.

The remaining material limits are immutable string copies outside active state, non-durable browser reload suppression, navigation-save failure, cleanup delays during outage or large sweeps, and broader distributed account/session mutations beyond one exact approval. Successful send feedback acknowledges the domain result; it does not prove inbox receipt or password completion. No live SMTP, real-device IME, physical zeroization, deployed topology, or universal distributed-support evidence is claimed.

For accessibility context, [W3C's Understanding SC 4.1.3](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) explains that action-result messages added without a context change should be programmatically identifiable for assistive technology.
