### P4 — R4 / AC4: recurring bounded cleanup with purpose isolation

Evidence: EmailPasswordChangeService.kt stores expiry only inside EmailPasswordChangePayload, enforces exact expiry during POST/GET, and deletes on issuance compensation or consumption. DeepLinksRepo.kt is only KeyValueRepo, while ExposedDeepLinksRepo.kt delegates to a two-column JSON text table. Email Plugin.startPlugin currently starts no cleanup. Password links are deliberately read-only on GET; registration links are separate handler records and remain repeatable.

Recommendation: implement an Email-owned expiry policy and recurring application-lifecycle worker that also operates when SMTP is disabled. Give deeplink storage a bounded, deterministic keyset-page scan and a conditional-delete capability, then let the Email worker inspect only email.password_change records with a decoded EmailPasswordChangePayload and expiresAtEpochMillis <= now. Process a fixed maximum page size, advance by stable opaque id, yield between pages, restart from the beginning after each complete sweep, and wait a fixed interval between sweeps. Process old persisted records as well as newly minted records; a worker holding only newly issued ids fails restart/backlog acceptance. Never load the whole table, use offset pagination while deleting, or stop after a permanent first page. Cancellation belongs to the application scope and stops the worker on shutdown. Ordinary failures are sanitized, retried in a later sweep, and must not silently kill cleanup.

Raw-page iteration should isolate undecodable JSON records so one malformed unrelated row cannot stop valid password cleanup; log counts rather than mailbox, fingerprint, UUID, or serialized payload. Delete only the exact decoded record previously inspected, using the atomic expected-value operation recommended in P5. Unknown handler ids, registration verification, other deeplink payloads, unexpired approvals, and exact expiry semantics remain unchanged. The generic storage/service API must not import Email's payload or policy.

A concrete feasible default is pages of 128 records and a one-minute delay between complete sweeps, with cooperative yielding between bounded pages. Retention is bounded by expiry plus sweep scheduling and backlog processing under a healthy running server; do not claim a fixed one-minute deletion guarantee regardless of backlog, database failure, or downtime. If the intended requirement is a hard wall-clock retention bound at a specified sustained arrival rate, the candidate must instead choose indexed nullable purpose/expiry metadata and state its capacity assumptions. That alternative requires idempotent nullable schema initialization and bounded backfill of legacy password records; it is operationally more complex than a bounded sweep. The complete candidate must settle the scan/metadata alternative and lifecycle registration rather than leaving implementation to guess.

### P5 — R5 / AC5: atomic shared-storage consumption; deployment remains unknown

Evidence: EmailPasswordChangeService.kt at lines 157–164 rereads the exact payload, calls removeDeepLink, and always returns true after that Unit-returning call. DeepLinksService.removeDeepLink delegates to repo.unset. MicroUtils' ExposedKeyValueRepo.kt and AbstractExposedKeyValueRepo.kt use a database delete count internally but discard that count from the public unset result. Two service instances with distinct Email coordinator and Auth locks therefore cannot distinguish the winner. server/deploy.sh and nonsudo.deploy.sh publish images; server/Dockerfile starts one JVM per container. These files do not specify replica count, rollout overlap, database sharing, or production topology. Auth README's in-memory sessions are additional process-local behavior, not proof of single-process deployment.

Recommendation: expose a narrowly specified atomic storage operation, such as removeIfEquals(id, expectedInfo): Boolean. For Exposed, perform one transaction deleting by primary key and the exact stored JSON value, and return true only for one deleted row. Preserve the original serialized record from the read when necessary: decoding and re-encoding must not accidentally reject older compatible JSON solely because default emission/property layout changed. An atomic transaction can alternatively lock/read the raw row, decode/compare, delete, and return its count; the database boundary, not a local Mutex, supplies exclusivity. Explicit implementations are required in fake/in-memory repositories; do not add a default get-then-unset fallback that claims atomic semantics.

Replace only the consume callback's unconditional remove/true with the conditional operation. All authorization checks remain before consumption. AuthFeatureService.setPasswordIfAuthorized at lines 335–364 already hashes outside the locked callback and performs consume then password write in NonCancellable; preserve that sequencing and active sessions. A loser must return InvalidApproval and never write. A consume failure must never grant permission. If consumption commits and the password write subsequently fails, the approval remains spent and the error propagates; no rollback/recreation of the approval and no false Changed result. Atomic consumption fixes reuse of the same approval across processes. It does not establish distributed linearization for unrelated role/email/admin mutations or promise comprehensive multi-process session support; those are outside this finding and must not be advertised as fixed.

External evidence: PostgreSQL's [Read Committed documentation](https://www.postgresql.org/docs/current/transaction-iso.html) states that a competing DELETE waits for the prior writer and ignores a row deleted by the committed writer. That supports the affected-row winner rule for a primary-key conditional delete. JetBrains' [Exposed CRUD documentation](https://www.jetbrains.com/help/exposed/dsl-crud-operations.html) specifies that deleteWhere returns the number of deleted records. Current documentation labels Exposed 1.5.0, whereas the repository pins 1.4.0; the local MicroUtils source already imports org.jetbrains.exposed.v1.jdbc.deleteWhere and uses its count, so the proposal depends on the installed repository pattern rather than a new 1.5 API. Compilation and actual storage tests are still required.

Tests: at repository level, create two independent repository instances/connections against one disposable PostgreSQL schema, synchronize both callers after reading the same raw record, and race conditional consumption; assert exactly one true and one false and row absence. At service level, use two independent coordinator/Auth/service graphs sharing the real approval and password stores; synchronize the consumption attempt, submit two different passwords, and assert exactly one Changed, one InvalidApproval, one password write, and the stored password matches the winner. A single graph or shared coordinator would repeat existing local-Mutex coverage rather than prove R5. Include missing/changed/wrong-purpose record, cleanup competition, failed consumption, consumption followed by password-write failure, and cancellation before/after the NonCancellable region. Retain existing one-instance concurrency and session-preservation tests.

Disposition: preferred mitigation even if the eventual topology is one process; the review remains a conditional deployment risk until operator evidence resolves applicability. Merely documenting single-process support is an authorized alternative, but requires an explicit operator deployment decision and prohibition on overlapping processes during rollout.
