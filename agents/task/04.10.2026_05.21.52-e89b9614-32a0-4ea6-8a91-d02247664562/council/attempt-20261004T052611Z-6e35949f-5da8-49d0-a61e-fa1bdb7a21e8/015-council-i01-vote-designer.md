## Decision and blocking issue

The terminal password form, safe navigation, cleanup, storage consumption, and preserved commit/session choices are acceptable. One narrow correction is required before I can consent to implementing the complete candidate unchanged: its instruction to retain the existing profile-change invalidation cannot satisfy its own unchanged-address Refresh recovery specifications.

Issue D2-R1 is an objection under D2, with designer as originator. The violated requirement is AC2's truthful independent delivery/read feedback together with AC7's complete, internally consistent implementation and regression contract. Candidate line 72 says that address-bound feedback may be retired according to the existing applyOwnedEmailProfile policy and that the existing invalidation works correctly after publication. The candidate's AC2 tests simultaneously require an unchanged owner/address to retain Sent after Refresh and read recovery. Those instructions disagree with the actual helper behavior.

Repository evidence is features/ui/users/src/commonMain/kotlin/ui/UserEditViewModel.kt:481, where requestOwnedEmailRefresh clears _ownEmailProfileState before any read, and lines 591–593, where applyOwnedEmailProfile compares the incoming profile against that now-null state and clears _passwordChangeEmailResultState. A returned approved email therefore appears changed even when it is exactly the address that owned the previously acknowledged request. A null or wrong-owner reconciliation also clears the profile at line 737, creating the same problem during a later successful recovery. The programmer's completed P2 proposal, reproduced in the issue snapshot, explicitly identifies this reset problem; the candidate retains only its alternative disposition and supplies no remedy for temporary profile absence.

The concrete failure is: POST returns Sent; a subsequent GET fails or returns no usable owner profile; Sent correctly remains with read feedback; the user chooses Refresh; the same approved address is returned; existing applyOwnedEmailProfile deletes Sent because previous is null. Even without the first failure, an ordinary successful Refresh clears the profile before reading and can retire the acknowledged result. This is not an authoritative recipient or approval change. The result disappears precisely during the read recovery the candidate promises will retain it. Reordering only the initial publication does not fix this behavior.

This is a prerequisite implementation-contract correction, not an optional note or a demand to retain feedback across every genuine address change. I retain my original policy that a checked authoritative recipient/approval change may retire recipient-bound feedback without fabricating delivery failure.
