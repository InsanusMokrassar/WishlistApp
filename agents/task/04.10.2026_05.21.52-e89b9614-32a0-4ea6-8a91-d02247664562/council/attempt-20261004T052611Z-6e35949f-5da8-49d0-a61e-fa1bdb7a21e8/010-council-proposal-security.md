No live deployment vulnerability or incident is asserted.

Recommendation: an atomic, expected-record consumption operation in shared storage is the narrow direct defense against two processes accepting the same approval. Its transaction must return success only when one still-matching password-purpose record is actually deleted; zero affected rows, mismatched handler/payload or a storage exception must authorize no password write. Use conditional DELETE or a transaction that locks, checks and deletes the exact persisted record. A separate read followed by ordinary Unit deletion is insufficient. Preserve the current consume-before-write choice: durable consumption precedes the hash update, and password-write failure does not restore the approval. That tradeoff permits a spent link after a failed write and requires the unknown-result recovery already covered by AC1.

Do not claim that atomic link deletion alone makes the entire application safe for multiple processes. Current-email and credential-state validation, other password mutations and session storage have additional process boundaries. If supported deployment remains one server writer, explicitly document that boundary, including overlapping rolling replacements; no password/credential authority redesign is needed for that choice. If multiple processes must be supported, the final design must specify how relevant current-email and credential-state checks stay consistent with consumption and the password write, rather than infer distributed consistency from a local lock.

## Research, invariants and documentation expectations

The [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), read on 4 October 2026, recommends single-use expiring reset capabilities, subject binding, trusted reset destinations, avoiding automatic login, and preventing referrer leakage. These principles support preserving the current authorization and navigation boundaries. OWASP also recommends session invalidation options; AC6 explicitly retains sessions for this reviewed change, so that recommendation does not authorize a session-policy redesign.

The [PostgreSQL transaction-isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html), read on 4 October 2026, explains that an ordinary read uses a statement snapshot, while concurrent deletion waits for a competing writer and ignores a row already deleted after that writer commits. The recommendation to inspect the actual deletion result follows from those database semantics; wrapping the existing read and unchecked delete in application-local locking cannot provide the same guarantee across processes.

AC6 regression expectations accompany every server change: keep sessions usable, create no new session, grant/revoke no roles, use only approved-current email, reject subject mismatch/revocation/stale fingerprints, preserve generic public failures, retain no-store/no-referrer route policy, and keep GET read-only. After durable consume and simulated password-write failure, verify no approval resurrection. The existing negative matrices in `EmailPasswordChangeServiceTest.kt:234–284` provide useful controls and should be retained.
