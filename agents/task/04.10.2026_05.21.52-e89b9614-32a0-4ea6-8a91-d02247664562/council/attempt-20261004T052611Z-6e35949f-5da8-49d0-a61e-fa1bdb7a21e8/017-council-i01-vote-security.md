## Blocking comment SEC-I01-01, attached to SEC-02

The candidate does not yet give a consistent implementation contract for preserving delivery feedback across an unchanged recovered profile read. This violates the candidate's own AC2 recovery specification and the unchanged-recovery expectation recorded in SEC-02. The objection concerns a concrete read-state distinction, rather than a preference to retain every historical outcome indefinitely.

In its delivery section, the candidate permits authoritative approved-address changes to retire feedback “according to the existing applyOwnedEmailProfile policy” and explains that publishing before apply makes “that existing invalidation” work correctly. However, the same candidate's AC2 tests require an unchanged owner/address to retain Sent through explicit Refresh and recovery. The existing policy cannot meet both instructions: `UserEditViewModel.kt:467–485` sets `_ownEmailProfileState.value = null` before every Refresh; `applyOwnedEmailProfile` at lines 587–594 compares the incoming email and approval flag with that transient null profile and clears `_passwordChangeEmailResultState` when either differs. Thus even a successful unchanged approved-address Refresh erases Sent. A null or wrong-owner reconciliation also nulls the profile at lines 738–746, producing the same false comparison on later recovery. Merely moving the request-result publication before reconciliation leaves this behavior unchanged.

The concrete failure sequence is: an approved owner requests an email and receives Sent; the independent GET fails; Sent correctly survives the immediate failure; the owner chooses Refresh; the unchanged approved profile returns; the existing null-versus-profile comparison removes the acknowledged result despite no authoritative recipient change. The candidate explicitly promises and tests retention for that sequence, while directing reuse of an invalidation predicate that removes the result. The implementation report must resolve the contradiction before implementation, rather than require an implementer to invent the missing feedback identity policy.

Security's proposed exact correction to the delivery implementation section is:

“Bind password-email feedback to the checked owner generation and captured approved-current recipient when publishing the request outcome. Keep that small in-memory feedback identity separate from the currently loaded profile. A null profile caused by Refresh, a failed GET, or a missing/wrong-owner GET does not by itself retire the checked address-free request result. On a later successful same-owner profile read, compare the authoritative current email and approval with the feedback identity rather than the transient previous profile: preserve feedback for the unchanged approved recipient and retire feedback for an authoritative recipient or approval change without converting the acknowledged outcome into delivery failure. Clear feedback and its identity together on a newly admitted operation, existing eligible-edit invalidation, owner/session/target invalidation and node destruction. Keep raw owner gates, load-failure admission, dirty drafts and all unrelated email-feedback policies unchanged. No HTTP receipt DTO or persisted mailbox record is introduced.”

The existing recovery test specification should then explicitly cover Sent followed by each of a thrown GET, null GET and wrong-owner GET, followed by one or more successful same-owner Refresh reads returning the unchanged approved address. Sent must survive, load failure must clear, and no POST may occur. The changed-address and approval-revocation cases should explicitly retire feedback without delivery-failure copy, including a change first observed after a failed read. Add a privacy assertion that the feedback identity is cleared with the outcome on owner-generation invalidation. These are targeted additions to the existing planned common-state cases, not a new testing surface.

The UI Architecture Notes outcome paragraph should add this exact sentence: “Refresh and failed profile reads do not erase the checked feedback identity; only a successful authoritative recipient or approval change, a newly admitted operation, eligible-edit invalidation, or owner/node invalidation retires that feedback.” This preserves the candidate's selected recipient-bound policy and its existing privacy constraints. This correction is a prerequisite, so the vote is DISAGREE rather than conditional acceptance.
