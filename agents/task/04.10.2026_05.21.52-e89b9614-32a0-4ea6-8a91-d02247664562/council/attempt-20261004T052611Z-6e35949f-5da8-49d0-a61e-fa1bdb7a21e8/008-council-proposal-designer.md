## Recommended user journeys and concrete changes

### D1 — Treat uncertain completion as a stable nonretryable page state

Add a UI-confined terminal uncertainty latch or an equivalent explicit submission-phase state in `PasswordChangeViewModel`. Set the state as soon as completion returns null, before releasing loading. Include the state in derived submit availability, the raw submission callback guard, and field-change admission. Field changes must not erase the uncertainty message. Keep successful completion distinct from uncertainty; never route an unknown operation to `Completed` or show `passwordChanged`.

On all three password renderers, an uncertain page must show the unknown-result message and a usable Continue/return action. Disable or remove the password editing controls as well as the submit control. Keep the existing safe exit delegate. Clearing fields when the user exits remains mandatory. Clearing fields immediately for uncertainty is an acceptable additional privacy choice if explicitly included in the candidate and tests; AC3 itself requires immediate clearing for denial.

Suggested exact English uncertainty copy is: “The password change could not be confirmed. Your password may have changed. Do not submit this link again. Continue to the app and try signing in with the new password.” Suggested Russian copy is: “Не удалось подтвердить смену пароля. Пароль мог измениться. Не отправляйте эту ссылку повторно. Вернитесь в приложение и попробуйте войти с новым паролем.” These strings do not assert failure or success. Trying to sign in is ordinary authentication and must not issue another completion POST.

The reviewed defect concerns resubmission from the existing `Unconfirmed` form. A local terminal state plus persisted safe exit repairs that defect. Browser refresh before exit can recreate a Pending route, and reopening the original email can create another page; the plan must not claim durable prevention across arbitrary reloads without a separately specified credential-free unknown-result route or persisted submission receipt. Such a broader receipt design is outside this proposal's selected narrow remedy.

### D2 — Preserve acknowledged delivery while showing read failure separately

In `UserEditViewModel.onRequestPasswordChangeEmail`, publish the typed issuance result after the existing owner/mutation checks, then reconcile the profile as independent work. A failed GET must use the existing load-failure surface and leave `Sent` visible. It must not synthesize `DeliveryFailed` or `PasswordChangeRequestFailed`. Continue checking current mutation ownership after every suspension; publishing before reconciliation does not authorize disclosure after logout, caller change, or live target change.

Do not require profile read success as evidence that the earlier POST returned Sent. Conversely, a fresh contradictory profile must not be treated as proof that no email was sent. The existing profile-change reconciliation may retire recipient-bound feedback, but subsequent copy must describe changed eligibility/profile state rather than failed delivery. Retained Sent is an acknowledgement of the request, not a promise that the link remains usable or that the mailbox received the message.

For a null issuance outcome, replace the false delivery-failure mapping with explicit uncertainty. Suggested English copy is: “The password-change email request could not be confirmed. Check your inbox before requesting another link.” Suggested Russian copy is: “Не удалось подтвердить запрос письма для смены пароля. Проверьте входящие перед запросом новой ссылки.” Keep the existing delivery-failure copy for the explicit `DeliveryFailed` domain result. This change belongs in `UsersListStrings.kt` and the three owner-email renderer mappings.

Refresh must issue only the existing profile/capability reads. A failed reconciliation must not trigger an automatic resend. The existing enabled-SMTP, approved-current, authenticated-owner admission rules remain; an email draft or pending replacement must never become the password-link recipient.

### D3 — Clear denial secrets and provide an outcome-neutral exit

Set both backing fields to empty strings in the same UI-confined denial handling that sets terminal invalid approval. Continue ignoring later field callbacks and submission callbacks. Do not leave a visually editable field whose callback silently refuses changes: render the controls disabled or omit the form on denial.

Add Continue to the JS denied state and show the same outcome-neutral action for uncertainty. Native Back already uses the safe delegate and should remain usable; adding the same Continue action is a consistent optional choice. Exit reaches the users list and does not claim the password changed, log the user out, clear sessions, or auto-request a link. A signed-in user can request a fresh link through the existing profile editor. An anonymous user uses the existing sign-in path; this task does not add unauthenticated issuance.

The current InvalidApproval copy may remain, since it says the link is unusable rather than claiming a preceding operation failed. Documentation and tests must say that application field references were cleared; immutable-string physical zeroization is not established.

### D4 — Preserve expired-link behavior while bounding storage retention

The implementation candidate must specify the cleanup owner, startup behavior, recurring interval, batch/work bound, exact expiry predicate, failure recovery, and shutdown/cancellation behavior. Periodic cleanup or database expiry metadata is preferable to cleanup triggered only by link opening or issuance, because unused approvals must age out during idle operation. Deleting at expiry does not shorten authorization: equality is already rejected.

Apply cleanup only to password-purpose approvals with validated expiry metadata. Unexpired approvals, registration-verification links, unrelated handler types, and records that cannot safely be identified as password approvals must survive. Public expired-link behavior remains generic 404/unhandled or terminal denial; do not add mailbox, account-existence, or credential-fingerprint disclosure. If bounded batches are selected, define how a large backlog drains and state retention honestly: a batch bound alone is not an unconditional wall-clock retention limit under arbitrary issuance load.

### D5 — Resolve supported deployment without overstating the finding

Prefer shared-storage atomic compare-and-consume when feasible, with a definite success/failure receipt controlling whether Auth writes the password. Exactly one consumer of the same approval may reach the write. Preserve consumption before the hash write and the existing session policy. Atomic same-approval consumption does not establish global serialization of different approvals, email changes, or all account mutations across processes; avoid documenting that broader guarantee without proof.

Alternatively, a one-process supported-deployment restriction must explicitly cover multiple containers, workers, and overlapping rollout instances sharing the same database. The Dockerfile alone does not enforce that restriction. The required operator question appears below. No newly observed evidence upgrades R5 to a confirmed deployed vulnerability.

## Proposed complete UI Architecture Notes addition

Append the following prose under Architecture Notes in `features/ui/users/README.md`, adapting only identifiers to the accepted implementation. The paragraph is intended content, not a claim that implementation or tests have already run:

“Email-authorized password-change feedback separates retryable input rejection, confirmed completion, terminal approval denial, and unconfirmed completion. Mismatch and InvalidPassword permit correction while the approval remains eligible. InvalidApproval clears both application password fields and permanently disables submission from the current page. Unconfirmed keeps the outcome explicitly unknown and permanently disables current-page submission, including native form Enter, IME Done, direct callbacks, and attempts to edit away the feedback. Terminal pages provide the existing safe Continue path to the users list; Continue clears transient fields and the root-owned navigation transition replaces and persists the exact approval page. Confirmed Changed alone produces the credential-free Completed success screen. Clearing immutable strings removes application field references and does not guarantee physical memory zeroization. A page-local terminal state does not claim durable replay prevention across arbitrary browser reloads or newly opened links.”

“The owner profile editor records password-change issuance outcomes separately from private profile reconciliation. An acknowledged Sent result remains truthful when a subsequent GET fails; read failure is displayed through the profile-load recovery surface and Refresh does not resend mail. Explicit DeliveryFailed retains delivery-failure feedback, while a missing transport result is presented as an unconfirmed request with an instruction to check the inbox before another request. Current-owner, live-target, mutation-generation, and cancellation checks still guard private feedback. Authoritative recipient/approval changes may retire recipient-bound feedback but do not establish that an acknowledged email was never sent. The approved current address remains the recipient while a replacement is pending or email-change cooldown is active.”

“Shared state tests and the existing JS browser, JVM Compose, and Android Robolectric hosts cover terminal submission admission, visible recovery, denial field clearing, and platform feedback. Client navigation tests cover approval-free exit persistence without transport replay. These hosts do not claim physical string zeroization, mailbox receipt, physical-device behavior, or live assistive-technology announcement behavior.”

The accepted candidate must also supply the complete email/deeplink retention and deployment/atomic-consumption Architecture Notes additions once the storage mechanism is selected. Those notes must state concrete cleanup timing/batch limits and remaining failure bounds, conditional deployment applicability, exact one-use guarantees, and preserved sessions/consume-before-write policy.
