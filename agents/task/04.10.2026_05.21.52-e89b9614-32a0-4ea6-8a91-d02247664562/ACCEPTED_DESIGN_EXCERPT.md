## External best-practice research

Research was performed on 4 October 2026 with the native web tool and primary sources. Recommendations below adapt the researched principles to the established feature boundaries.

The [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html) recommends expiring, one-use approval tokens and matching the application's password policy. This supports preserving the existing expiry and policy while enforcing one-use in persistent storage. Additional recovery-product changes, new notifications, and session invalidation are outside the reviewed scope; existing sessions remain available as expressly required by AC6.

[RFC 9110 section 9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) limits retries of non-idempotent operations when the caller cannot establish whether the request was applied. The existing completion POST has no durable completion receipt for the UI to query. Therefore an unknown response should permanently stop the current form, rather than introduce a guessed retry or infer failure from a later approval rejection.

[PostgreSQL's transaction isolation documentation](https://www.postgresql.org/docs/current/transaction-iso.html) explains that concurrent DELETE at Read Committed waits for conflicting writers and evaluates the applicable updated row. [PostgreSQL DELETE](https://www.postgresql.org/docs/18/sql-delete.html) defines results in terms of rows actually deleted. [Exposed CRUD documentation](https://www.jetbrains.com/help/exposed/dsl-crud-operations.html) exposes deleted-row counts through deleteWhere. Adaptation: use the existing Exposed stack, a predicate over the exact persisted id and raw JSON, and the committed affected-row count. This avoids a dependency upgrade or a PostgreSQL-only RETURNING requirement. A local mutex and a read followed by Unit-returning unset are rejected as insufficient storage authorization.

[PostgreSQL LIMIT/OFFSET guidance](https://www.postgresql.org/docs/16/queries-limit.html) requires predictable ordering for bounded page selection. Adaptation: use an ordered keyset cursor over the actual stored key/value primary-key pair and a sweep high-water mark. OFFSET is rejected because deleting earlier records can skip later records. Per-page transactions and finite sweeps avoid holding one transaction over the whole table.

[Kotlin cancellation guidance](https://kotlinlang.org/docs/cancellation-and-timeouts.html) supports explicit cancellation propagation and bounded NonCancellable cleanup. The proposal preserves existing commit cancellation behavior and attaches the maintenance loop to the server's injected lifecycle scope; maintenance cannot own an unrelated global scope.

### Storage-level conditional deletion

Add `features/deeplinks/common/src/commonMain/kotlin/repo/MaintainableDeepLinksRepo.kt` as an additive interface extending DeepLinksRepo. Define the small supporting cursor/record/page types in that file or a companion internal-storage model file. A cursor contains the stored DeepLinkId and raw serialized info; a scanned record contains the same pair. A page is ordered and advances using the last scanned raw row. ### Expired unused approval cleanup

Add `features/email/server/src/commonMain/kotlin/services/EmailPasswordChangeApprovalCleanup.kt`. The constructor accepts nullable DeepLinksService, the production Json, an injectable epoch-millisecond clock, and the server lifecycle CoroutineScope when started. `cleanupSweep()` captures a database-order high-water cursor and walks through that finite range in pages of at most 100. Each scan is a separate short transaction. Decode each row independently; delete only a record whose handler is exactly `EmailPasswordChange.handlerId`, whose decoded value is EmailPasswordChangePayload, and whose `expiresAtEpochMillis <= now`. Delete with `consumeDeepLink` against the observed info, so changed or concurrently consumed rows cannot cause removal of unrelated state. Unknown serializers, malformed rows, other handlers, other payload types, and unexpired password approvals remain untouched. Advance using the raw last scanned row even when decoding fails. Require the scan and high-water query to use the same database ordering and the complete key/value pair; do not order in Kotlin or use OFFSET.

At startup, launch one maintenance coroutine per server process in the injected lifecycle scope. Run an immediate sweep, then delay 60 seconds after each completed sweep before beginning another. Yield between pages; do not retain all links in memory or put SMTP/profile work under the maintenance transaction. Capturing a high-water mark prevents continuing inserts from extending one sweep indefinitely. Raw SQL errors and individual deletion errors should be logged with a fixed sanitized message, without id, address, fingerprint, raw JSON, or approval value. Ordinary per-record deletion failures should allow the remainder of the sweep to proceed and be retried next sweep; scan errors abort the current sweep and retry after the normal delay. Cancellation always propagates, stops new page work, and is not converted into a delivery or domain outcome. Do not spawn GlobalScope or a daemon detached from shutdown.

Register the cleanup singleton unconditionally in Email's `Plugin.setupDI` and start it in `Plugin.startPlugin` using `koin.get<CoroutineScope>()`. Maintenance must run when SMTP is disabled, because links issued before SMTP disablement still exist. Absent deeplinks or absent maintenance storage produces an idle/no-op cleaner and password issuance remains Unavailable; no construction cycle is introduced. An idempotent start guard prevents duplicate loops if the same plugin instance is started twice. Multiple processes may run cleanup concurrently; conditional deletion makes their overlap safe.

This is bounded cleanup: 100-row memory/query pages, finite captured sweeps, and a 60-second interval independent of traffic or link opens. For healthy storage, a record already present before expiry is removed by a sweep that observes expiry; a record inserted behind an active cursor is reached after the next reset. The operational retention bound is the scheduled interval plus the relevant finite sweep duration; there is no promised hard wall-clock SLA during outage, process suspension, deletion failure, or unbounded table growth. Sweep duration grows with total generic deeplink population, a known tradeoff for retaining the existing schema and handling previously issued approval records. No schema column, backfill, rewrite, or expiry policy for registration links is introduced. Startup sweep handles previously stored password approvals without separate migration. If a fixed volume-independent retention SLA is required, that would be a separate explicit requirement for indexed expiry metadata.

## Alternatives, compatibility, rollout, and risks

A single-process restriction would also satisfy the conditional review recommendation but would require an operator choice about supported deployment and could leave the underlying one-use contract dependent on mutable deployment assumptions. The recommended atomic consume avoids that choice and uses existing shared storage. Making consume plus password write one transaction with rollback would change the explicitly reviewed burn-before-write semantics and is rejected for AC6. Receipt/idempotency endpoints, session revocation, a password-recovery redesign, and distributed account-lock infrastructure are excluded.

For cleanup, removing records only when GET/POST encounters expiry cannot reach never-opened approvals and is rejected. An issuance-triggered sweep cannot clean idle installations and is rejected. Loading getAll into memory has unbounded memory cost and is rejected. Adding indexed purpose/expiry columns is credible for larger scale, but requires metadata/backfill/schema work beyond the narrow repair; finite raw keyset sweeps remove existing approvals without changing unrelated payloads or storage layout. The concrete limits and operational retention caveat above must be documented honestly.

No application data or wire migration is required. Existing serialized password approvals retain their expiry and serializer identity; startup cleanup handles old records. The persistence capability is additive and generic DeepLinksRepo consumers retain behavior. Alternate storage that lacks the capability cannot issue redeemable password links until it implements the contract. No dependency upgrade or production configuration key is planned.

Deploy server and UI fixes together following the existing feature rollout constraints, including invalidation of old web assets; old clients can retain the reviewed retry behavior. Stop old server processes before relying on the atomic-consumption guarantee, because old binaries can still use unconditional deletion. This is a compatibility constraint, not evidence of multiple running replicas. Retain the database backup and the existing timestamp/lifecycle rollout checks from feature documentation; do not introduce data rewrites.

Rollback of these source changes restores the reviewed unsafe behaviors and cannot restore deleted expired/consumed approvals. Use a compatible forward repair when possible. If reverting the feature repair, stop all writers first and preserve the prior application's own rollback constraints. No compensating recreation of a used approval is allowed. Cleanup outages increase retained expired metadata but do not make expiry checks authorize an expired record.

Remaining risks are sweep cost proportional to generic stored records, delayed retention during outage, in-memory immutable-string copies outside active ViewModel state, and broader multi-process invariants outside same-token consumption. Error logs must remain free of approval and credential data. Confidence is high for the UI corrections and storage predicate, and medium-high for the proposed generic paging integration until the real repository and PostgreSQL tests execute. This council report claims planning and evidence review only.
