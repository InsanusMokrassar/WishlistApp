## F1: Recoverable promotion without restoring revoked access

The current role helper removes NewUser before adding User. A successful removal followed by a failed insertion erases the only authorization evidence that permits retry. Fix the existing helper under its existing roleTransitionMutex by retaining NewUser until direct User membership has been established. The coordinator continues checking the exact current address and persisting email approval before calling the role helper; keep coordinator-then-role lock ordering and SMTP outside both locks.

The operation order is explicit. Read direct roles while holding the role lock. If direct NewUser exists, first ensure direct User exists, calling includeDirect only when User is absent. Confirm direct User before removing NewUser. Then call excludeDirect for NewUser and confirm the resulting direct state contains User and no NewUser before returning success. Preserve SuperAdmin and every unrelated role throughout. The NewUser branch takes precedence when both NewUser and User exist, so a retry completes pending-marker cleanup instead of returning early.

When direct NewUser is absent, existing direct User succeeds without role writes. Existing direct SuperAdmin also permits the address-verification result without adding User or rewriting SuperAdmin; SuperAdmin alone must not become a substitute for Auth's direct-User login check. A subject with none of those direct roles returns false without any grant. Inherited roles, the emailApproved Boolean, and a historical link do not authorize a User insertion. If an administrator removed all qualifying direct roles between attempts, the next attempt remains denied, even after a prior partial transition.

An ordinary includeDirect failure propagates and does not attempt NewUser exclusion. NewUser therefore remains available for retry, including a failure thrown after User was actually inserted. An ordinary exclusion failure also propagates; User has already been established, while NewUser may remain or may have been removed before the exception. A subsequent call finishes cleanup or succeeds idempotently. Do not compensate by removing User, which would introduce a second destructive transition and could erase pre-existing access. An unsuccessful confirmation returns false without reporting a successful transition; repository exceptions and cancellation propagate.

This sequence deliberately allows direct User to remain after email approval and a failed NewUser cleanup. Auth already authorizes direct User, so login may become available after that committed grant even though the link request failed. The grant is valid because address verification and the direct pending guard preceded it. Do not change Auth to deny such accounts or claim cross-repository atomicity. The failed callback must not emit a success redirect or confirmation, and reopening the exact link must converge on User without NewUser. Durable approval remains true across an ordinary role failure; retry must still invoke promotion when approval is already true.

Acceptance requires deterministic role tests for an insertion failure before mutation, insertion followed by an exception, exclusion failure before removal, and exclusion followed by an exception. Recover the fake repository and repeat the same call; assert the intermediate direct roles, eventual success, and operation order. Cover NewUser alone, NewUser plus User, NewUser plus SuperAdmin, User alone, SuperAdmin alone, repeated success, inherited-only membership, and a fully revoked subject. A coordinator/handler integration test must prove persisted approval survives a one-time role failure, the first attempt produces no success result, and the same link later completes.
