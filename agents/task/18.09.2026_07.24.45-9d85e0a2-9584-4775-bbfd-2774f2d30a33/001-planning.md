## Task understanding and resolved scope

Pending email verification state must belong to an email-feature model. RegisteredUser, AuthFeatureUser, AdminUser, and their forward/reverse mappings must no longer contain pendingEmail or a request timestamp, including nested substitutes that merely retain the same dependency through a user model. Move the associated emailChangeAllowedAt metadata off these user models too, and expose the complete owner email state through EmailFeature. The current stored email and emailApproved may remain on private identity/auth/admin models because the request does not remove existing approved identity information. Public UsersFeatureUser remains exactly id and username. Before first approval, current email continues to hold the unapproved first candidate, preserving the accepted lifecycle.

The new requested-at time and existing cooldown deadline are different facts. Record the server UTC epoch-millisecond time of an accepted write that introduces or replaces an address awaiting verification. This includes a newly created unapproved address and initial/unapproved replacements, as well as pending replacements after approval. The timestamp belongs to the candidate that currently needs verification. Same-current and same-pending saves, username-only mutations, reads, delivery attempts/resends, and failed/rejected operations must not rewrite it. Successful approval and explicit clear remove the outstanding request timestamp. A new pending candidate replaces the previous timestamp. Previously stored candidates have an unknown request time and remain null until a real new candidate write occurs; do not infer a request time from the approval deadline, migration time, link creation, or current clock.

Cooldown remains rooted at successful approval and is persisted independently as emailChangeAllowedAt. Configuration omission/zero, positive policy validation, exact-expiry admission, stale-link handling, approved-current retention, first-unapproved behavior, raw cross-slot uniqueness, explicit-clear behavior, and typed 429/409 contracts remain unchanged. Timestamp addition does not add a resend restriction, email expiry, generation token, policy, history, or UI control.

No operator question remains after resolving these routine implementation choices from the prompt and current code. No operator answer was required. Architecture may refine names and adapter placement while preserving the following explicit contract.

## Target model, endpoint, and dependency direction

Introduce a serializable email-owned owner profile in features/email/common/models, with current email, emailApproved, pendingEmail, emailChangeRequestedAt, and emailChangeAllowedAt, plus a response owner identifier. A flat model is sufficient; a separate nested pending-request type is optional only if it simplifies the implementation. All timestamps use nullable Long UTC epoch milliseconds, with null request time explicitly meaning unavailable for legacy state or no outstanding candidate. This is an email-feature DTO, not RegisteredUser or an AuthFeatureUser wrapper.

Keep the dependency direction users/common -> email/common. Email/common cannot import UserId from users/common without a cycle. A Long owner identifier on the email-owned wire model is an acceptable narrow representation; convert or compare it to UserId.long at existing user-facing boundaries. Preserve the current response-owner identity check in addition to captured owner-session/generation guards. Do not relocate the repository-wide UserId type or introduce generic identifier frameworks for this task.

Add authenticated GET /api/email/myEmail alongside the existing PUT. The server resolves callerId exclusively from bearer authentication and returns the caller's fresh email-owned profile. Do not accept a user-id request parameter or add an admin pending-email read. Existing accounts with no email return a valid empty profile; a concurrently missing account may return 404 mapped to null by the client. Other non-success responses, malformed bodies, and transport failures remain recoverable failures rather than an empty successful profile. Both SMTP-enabled and disabled implementations delegate this read to the same coordinator. KtorEmailFeature remains transport-only.

Expose a fresh email-profile read from the persistence boundary, returning the email-owned model from one users-row SELECT. The narrowest implementation can add a UserId-keyed read method to the existing repository interface and delegate through CacheUsersRepo directly to the backing implementation; the physical adapter may remain in users/common. Architecture should specify the exact method and placement, with no fallback that derives pending state from RegisteredUser or silently returns null when an implementation forgets the new capability. This request changes model/API ownership; it does not require moving existing columns to another table. Retaining the single row and existing transaction/lock avoids introducing a second-store atomicity problem or unnecessary data-copy migration.

Replace coordinator getCurrentUser pending-state reads with the fresh email profile. Introduce/reuse a narrow concrete sender entry point taking the exact user id and selected recipient, and have the existing registration hook delegate to the same delivery/compensation implementation using its unapproved current address. Owner verification must pass the email model's candidate, never construct a fake RegisteredUser with a replacement in its email field. Keep request-local link cleanup, SMTP outside the mutex, post-delivery recheck, stale/approved/missing classifications, and role transitions unchanged.

Retype or rename UsersModel.getMyProfile to clearly expose the email-feature profile, delegated solely to EmailFeature's owner read. DefaultUsersModel keeps auth meState for caller identity/permissions; an unused direct ClientAuthFeature dependency may be removed with its DI/tests. Retype ownEmailProfileState, private helper functions, snapshots, and renderer parameters to the email-owned model. Pending state must never be reconstructed from auth meState, public users, or AdminUser. ## Preservation and compatibility decisions

Remove pendingEmail and emailChangeAllowedAt from RegisteredUser, AuthFeatureUser, AdminUser, and their serialization/mappers. Do not add emailChangeRequestedAt to any of those models. The public reverse mapper requires only the remaining omitted current email and approval fields. Retain ordinary NewUser input and existing mutation signatures where practical; dedicated writes may still return the reduced RegisteredUser while internal lifecycle logic and explicit email reads use the email model. Auth/admin private DTOs keep current email/approval. Update KDoc and feature READMEs outside Operator Notes so the new ownership is unambiguous.

This is an intentional removal of fields from user wire payloads and an additive email read endpoint. Existing project Json ignores unknown keys, so a new client can decode older identity payloads; that is not sufficient for functional old-server compatibility because the owner email endpoint is new. An old UI against the new server defaults removed fields to null and may misinterpret pending state. Therefore deploy matching server/UI versions together and invalidate old web assets; do not claim mixed-version UI support or add a fallback through auth that violates ownership. No existing write/delivery route, success body, Boolean behavior, cooldown response, or deeplink payload changes are necessary.

## Migration, deployment, rollback, and forward repair

Expand the existing schema with nullable users.email_change_requested_at through the established additive initialization path. Retain raw current/pending values, approval flags, deadlines, unique/index definitions, and lock row unchanged. There is no data-copy backfill because no reliable historical request time exists; null is honest and preserves every legacy candidate. Repeated startup/reopen must be idempotent and must not restamp or rewrite existing state. New accepted candidate writes persist time atomically with the candidate, using the repository clock after lock acquisition. One sampled time should be reused for a mutation's admission/stamp when needed; no-op paths must not acquire a new semantic timestamp.

The implementation sequence is expand the email model/read capability and nullable storage, migrate internal readers and UI to the new endpoint, verify state and behavior, then contract the user domain/wire fields in the final deliverable. Each coding checkpoint should compile; obsolete adapter fields may exist only within the implementation sequence, not the final API. There is no physical table/column contraction or destructive cleanup in this task. Partial migration or startup failure must surface as a failure and remain retryable rather than silently serving a fabricated empty email profile.

Before deployment, back up the database and verify restoration. Stop old writers; add the column/initialize the new release; verify row values and unknown legacy timestamps; deploy matching clients and server before resuming traffic. Old binaries neither maintain the new timestamp nor understand the new profile ownership, so concurrent old/new writers are unsupported even when both share users_write_lock. Do not use old binaries to continue writes against upgraded data.

Prefer forward repair with the new schema and preserved raw values. An emergency rollback requires stopping writes and deploying a compatible backport that understands the retained lifecycle and request column, or restoring the pre-upgrade backup with explicit acceptance of post-backup data loss. Retaining legacy columns alone does not make old-version write rollback safe: old code can replace/clear a candidate while leaving an unrelated timestamp behind. Do not automatically drop columns, clear unknown times/deadlines, promote candidates, or erase pending state as rollback.
