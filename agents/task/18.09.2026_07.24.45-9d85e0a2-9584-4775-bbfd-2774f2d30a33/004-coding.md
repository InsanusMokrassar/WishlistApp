# Coding: email service, owner GET, and exact verification delivery

Implemented architecture checkpoint 3 only. The temporary legacy lifecycle fields on RegisteredUser, AuthFeatureUser, and AdminUser remain untouched. The profile-edit MVVM and final model/wire/documentation contraction are intentionally deferred to the following checkpoints; the only documentation changes in this checkpoint are KDocs required for the new APIs.

Both EmailFeature interfaces now expose `getMyEmail`: the server version takes the authenticated UserId and the client version resolves it through the bearer token. The Ktor client issues only `GET email/myEmail` with `expectSuccess = true`. It returns null only for Ktor's explicit 404 client exception. It decodes a non-null EmailProfile, so successful JSON `null`, a missing userId, invalid email text, malformed JSON, transport errors, cancellation, and every non-404 non-success status propagate rather than being accepted as an absent account.

The email Ktor configurator now exposes authenticated `GET /api/email/myEmail` under the existing `/email` route. It resolves the bearer caller before invoking the service, sends the fresh EmailProfile for any existing account including an empty profile, and returns 404 only after a missing-account read. The handler accepts no target identifier, and query selectors cannot change the caller. Existing public enabled, root-gated test-send, self PUT, and verification POST behavior remains unchanged.

EmailVerificationAccountCoordinator's former `getCurrentUser` method was renamed to `getCurrentEmailProfile`. It retains the existing mutex and calls the mandatory `UsersRepo.getEmailProfileFresh` inside the lock. EmailFeatureService and DisabledEmailFeature both delegate their read surface through this same coordinator, so email reads and storage remain available with or without SMTP and share the existing DI singleton with verification/deeplink mutation services.

EmailFeatureService now makes its before-SMTP and after-SMTP verification decisions from EmailProfile and the email-owned pending-first `verificationCandidate` helper. SMTP remains outside the mutex. The implementation preserves NoEmail, EmailChanged, AlreadyApproved, Unavailable, DeliveryFailed, and Sent outcomes; after delivery it rereads fresh state and rolls back only the request-local link for deletion, clear, replacement, or approval races. The request timestamp is carried by the profile but is not a generation check.

EmailRegistrationInviteSender now provides `sendVerificationEmailWithCompensation(userId, recipient)`. The new method mints the deeplink with precisely that id/address payload, delivers to precisely that address, preserves false/error/cancellation cleanup and NonCancellable rollback behavior, and returns a request-local delivery handle. The existing registration adapter now selects only an unapproved current RegisteredUser email, returns null for absent or already-approved current email, and delegates to the exact-recipient method. It never moves pendingEmail into a fabricated current user.

The email-server FakeUsersRepo now owns independently seedable EmailProfile values keyed by UserId. Fresh reads return the profile only while the user row exists; simulated write boundaries synchronize the temporary legacy user projection, while tests can observe fresh-read calls and injected errors. All EmailFeature test fakes in the router and UI modules explicitly implement the new method.
