## Overview

User identity storage and public read-only API. Provides the `UsersRepo` CRUD repository and `UserId`/`Username`/`User` domain models used across all features. Exposes a single public HTTP endpoint `GET /users/getAll` for listing all registered users. Client-side mirror feature allows consumers to fetch the user list.

## Routes

> All paths below are served under the global `/api` prefix (e.g. `/api/users/getAll`). The prefix is applied centrally by `features/common/server` (`InternalApplicationRoutingConfigurator`) and added on the client by `DefaultUrlHttpClientConfigurator`, which appends `/api` to the configured server base URL.

| Method | Path | Auth | Body / Response | Description |
|--------|------|------|-----------------|-------------|
| GET | `/users/getAll` | None | `List<UsersFeatureUser>` | Fetch all registered users (public-facing projection — no email) |

| `CacheUsersRepo` | In-memory `FullCRUDCacheRepo` wrapper |

## Architecture Notes

- **Server-side:** `UsersFeature` interface defines `getAll()` method returning all registered users, projected onto `UsersFeatureUser`. `UsersService` implements this interface, delegates to `ReadUsersRepo`, and maps each stored `RegisteredUser` via `asUsersFeatureUser()` before returning — this is what keeps `email` off the public listing. `UsersRoutingsConfigurator` (JVM) registers public endpoint `GET /users/getAll` (path constants: `usersPrefixPathPart = "users"`, `usersGetAllPathPart = "getAll"` in `features/users/common/Constants.kt`).
- **Feature Interface Return Model Rule (issue #67):** `UsersFeature.getAll()` (both server and client) returns `UsersFeatureUser`, not the `RegisteredUser` persistence entity — see `agents/CODING.md`'s "Feature Interface Return Model Rule" section for the repo-wide rule this fix established. `UsersFeatureUser` lives in `features/users/common/src/commonMain/kotlin/models/UsersFeatureUser.kt` alongside its `RegisteredUser.asUsersFeatureUser()` mapper.
- **Client-side:** Mirror `UsersFeature` interface + `KtorUsersFeature` implementation in `features/users/client/src/commonMain/kotlin/`, registered in `client/Plugin.kt` (consumed by `features/ui/users`).
- `server/Plugin.kt` is intentionally empty. `auth/server/JVMPlugin` calls `users.common.JVMPlugin.setupDI` directly to wire `ExposedUsersRepo → CacheUsersRepo → UsersRepo` into the DI graph.
- `singleWithBinds<UsersRepo>` registers `CacheUsersRepo` as `UsersRepo`, `ReadUsersRepo`, and `WriteUsersRepo` simultaneously.
- Root user bootstrap happens inside `auth/server/JVMPlugin.startPlugin`: if `UsersRepo.count() == 0`, creates a `root` user and prints generated password once via KSLog — see `roles/README.md` for which roles get granted to a newly created user and by what mechanism (issue #68).
- **Email field (added in issue #44):** `User`, `NewUser`, and `RegisteredUser` all carry `email: Email? = null` (defaults to `null` for back-compat). `ExposedUsersRepo` has a `nullable text("email")` column, now also `.uniqueIndex()`-constrained — `NULL` values are exempt from the uniqueness check under standard SQL unique-index semantics, so users without a stored email never collide with each other, while two users sharing the same non-null email throws `DuplicateUserFieldException` (see "Duplicate-key-to-409 convention" below). `createMissingTablesAndColumns` (via `initTable()`) adds the column, and now also the unique index, to existing tables on first startup after this change, without a separate migration step. Invalid stored values are read defensively via `Email.parse(...).getOrNull()`. `features/users/common` now depends on `features/email/common` for the `Email` type.
- Self-service email update is exposed via `PUT /api/email/myEmail` in `features/email/server` (not under `/users`) to keep the email-routing scope cohesive.
- **Current-email approval:** `ExposedUsersRepo` stores a non-null `email_approved` column with a database default of `false`. Inserts always begin unapproved. Lifecycle-aware writes preserve approved current state while a replacement is pending; username-only changes preserve every email field. `approveEmail(id, expectedEmail, cooldownMillis)` checks exact candidate identity atomically, clears the candidate's requested-at, roots `emailChangeAllowedAt` at approval, then mirrors a committed result into the cache and emits the normal update event only when durable state changed. This prevents stale verification links from approving a replacement address.
- **Approved/pending lifecycle:** Before the first approval, the unapproved candidate remains in `email` with `pendingEmail = null`; changing that candidate replaces the unapproved value and records a new accepted-write `emailChangeRequestedAt`. After approval, a replacement is stored only in `pendingEmail`, while `email` and `emailApproved` remain the latest approved state; the replacement records its own requested-at. Replacing a pending candidate releases the old candidate and replaces the timestamp. Approval promotes only the exact current pending candidate (or the exact unapproved first candidate), is idempotent for an already-approved exact current address, clears the pending slot and requested-at, and issues `emailChangeAllowedAt` from the configured cooldown. Stale or superseded links return no mutation. A legacy candidate with no reliable historical request time remains `null`.
- **Cross-slot ownership and writers:** Every users writer (`create`, single/batch `update`, dedicated email/username changes, approval, and delete) first updates the durable singleton `users_write_lock` row inside its transaction, then checks raw current and pending columns for address ownership. The participating-writer requirement covers all application mutations through `UsersRepo`; direct SQL and old binaries that skip the lock are outside supported live operation. The tradeoff is serialized users writes across otherwise unrelated accounts. Deployments must back up first, stop old writers, and roll out matching server/UI versions without mixed old/new writers; forward repair is preferred. An old binary is not a safe rollback target after migration: restore the pre-upgrade backup with post-backup loss disclosed, or use a compatible backport. No automatic lifecycle-data contraction occurs.
- **Events and reads:** Mutations publish repository events only after commit; no-op writes publish no changed event. Pending-only writes still publish the existing committed changed event even when reduced `RegisteredUser` values compare equal. `getByIdFresh` bypasses the id cache for fresh identity reads; the mandatory `getEmailProfileFresh` performs a separate fresh lifecycle projection and `CacheUsersRepo` delegates it directly without reading or updating the user cache. Cache mirroring occurs only after successful backing writes.
- **Compatibility and verification:** `email_change_requested_at` is additive, nullable, initialized idempotently, and never backfilled because historical request time cannot be inferred. Legacy rows retain raw email values and unknown requested-at state; reads do not restamp or repair rows. PostgreSQL lock/concurrency execution is a required disposable-database test gate, not a product claim; the gate remains pending when `WISHLIST_POSTGRES_TEST_JDBC_URL` is unavailable. Supported operation has a throughput cost from singleton serialization and does not include mixed old/new writers that bypass the lock.
- **Duplicate-key-to-409 convention:** `usernameColumn` and `emailColumn` are both `.uniqueIndex()`-constrained. `ExposedUsersRepo.update`/`create` override the library defaults (`AbstractExposedWriteCRUDRepo.update`/`create`) to catch `org.jetbrains.exposed.v1.exceptions.ExposedSQLException`, then consume `dev.inmo.wishlist.features.common.common.utils.isUniqueViolation`, which inspects every throwable cause and JDBC next-exception edge for PostgreSQL state `23505` or Xerial's exact `SQLITE_CONSTRAINT_UNIQUE`/`SQLITE_CONSTRAINT_PRIMARYKEY` result code. Matching failures become `dev.inmo.wishlist.features.users.common.repo.exceptions.DuplicateUserFieldException`; every other exception is rethrown unchanged. Traversal is iterative and identity-based so cause/next cycles terminate without merging distinct equality-colliding exceptions. Generic JDBC code 19, exception message text, base `SQLITE_CONSTRAINT`, and unrelated SQLite NOT NULL/CHECK/FOREIGN KEY/ROWID constraints are deliberately not translated. `CacheUsersRepo`'s `FullCRUDCacheRepo` write wrapper does not catch exceptions from the wrapped repo, so the exception propagates through it untouched. Consumers that need to distinguish "duplicate" from other failures catch `DuplicateUserFieldException` at the HTTP boundary and respond `409 Conflict` instead of the generic `500 Internal Server Error` an unmapped exception would otherwise produce (Ktor's engine-level `DefaultEnginePipeline.handleFailure` fallback). Current consumers: `features/email/server`'s `PUT /email/myEmail`, and `features/admin/server`'s `PUT /admin/users/update/{id}` and `POST /admin/users/create`. A future feature hitting the same shape (a unique-constrained write whose caller needs a distinguishable "duplicate" signal) should follow this same pattern rather than invent a new one.
